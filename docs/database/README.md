# База данных: карта документации

**Статус:** рабочий документ · версия 1.0  
**Связанные документы:** `../supabase-setup.md`, `solo-schema.md`, `finance-schema.md`, `erd.md`

## 1. Что здесь описано

Схема PostgreSQL, которая создаётся миграциями в `supabase/migrations/`. Одна и та же схема применяется к локальной среде и к production: различаются только данные, а не таблицы, ограничения и политики.

| Документ | О чём |
| --- | --- |
| [`solo-schema.md`](solo-schema.md) | Профиль и направление «Solo»: сферы, цели, вехи, привычки, задачи, выполнения, журнал наград |
| [`finance-schema.md`](finance-schema.md) | Направление «Финансы»: категории, серии, операции, базовые линии, снимки месяцев, ревизии |
| [`erd.md`](erd.md) | ERD-диаграммы Mermaid: обе схемы и связи между ними |

## 2. Источник истины

Схема меняется **только миграциями**. Файл миграции — это и есть окончательное описание таблицы; документы объясняют смысл и инварианты, но не заменяют SQL.

```text
supabase/
  migrations/
    20261114120000_profiles_and_solo.sql   профиль, RLS, Solo, журнал наград
    20261114120100_finance.sql             финансы, триггеры, функции, RLS
  seed.sql                                 локальные тестовые данные, на prod не применяется
  config.toml                              настройки локального стека
```

Правило продвижения: **локальная среда → `main` → production**. Обратное направление запрещено: данные из production не копируются на машину разработчика, а схема не правится руками в Studio.

## 3. Общие соглашения

| Соглашение | Почему так |
| --- | --- |
| Имена таблиц и колонок — `snake_case`, во множественном числе | Совпадает с PostgreSQL и PostgREST по умолчанию; меньше преобразований в коде |
| Первичный ключ — `uuid` (`gen_random_uuid()`) | Клиент может сгенерировать id заранее и повторить запрос без дубля |
| Пользовательские таблицы имеют `user_id` | RLS-политика фильтрует строки по `auth.uid()`; ведущая колонка индексов — `user_id` |
| Деньги — `bigint` в копейках | Точное сложение без `float`; дробные рубли не нужны |
| Календарные даты — `date`, моменты — `timestamptz` | Раздел финансов считает по дням; журнал progress требует момента подтверждения |
| `created_at` / `updated_at` — `timestamptz not null default now()` | Аудит и сортировка; `updated_at` обновляется триггером |
| Архивирование вместо удаления | История и журнал не должны терять контекст |
| RLS включена **явно** на каждой таблице | Новая таблица без RLS при наличии прав читается кем угодно |
| Политика использует `(select auth.uid())` | Значение вычисляется один раз на запрос, а не на каждую строку |
| Секретный ключ `service_role` не попадает в клиент | Он обходит RLS и предназначен только для серверных задач |

## 4. Что не хранится

Обе схемы следуют одному правилу: **хранится только то, что нельзя восстановить**.

| Не хранится | Где считается |
| --- | --- |
| Общий XP, общий уровень, уровень сферы | Сумма журнала `reward_ledger` и кривые домена `@solo/domain` |
| Ритм и серия привычки | История выполнений и расписание, домен `@solo/domain` |
| Фактический и целевой баланс | Базовая линия плюс операции, домен `@solo/finance` |
| Отклонение дня и текущего месяца | Домен `@solo/finance`; хранится только снимок закрытого месяца |
| Остаток плановой операции | `amount_minor` минус сумма связанных фактов |
| Агрегаты дня, месяца и категории | Запрос по операциям и доменные функции |

Кэш допустим только как оптимизация с явным признаком кэша. Для одного пользователя и десятков строк в день он не нужен.

## 5. Проверка схемы

```bash
npm run db:start        # локальный стек Supabase
npm run db:reset        # применить миграции с нуля и загрузить seed
npm run db:status       # адреса, ключи, состояние контейнеров
```

После `db:reset` проверяются три вещи:

1. миграции применяются на чистой базе без ручных правок;
2. seed создаёт тестового пользователя и тестовые данные;
3. неверные записи отвергаются базой: повторная награда, правка журнала, факт на пропущенный план, второй снимок месяца, удаление базовой линии.

Тестовый пользователь локальной среды: `test@solo.local` / `solo-test-password`. Письма Auth не уходят наружу — они лежат в Mailpit на `http://127.0.0.1:54324`.

## 6. Правила безопасности

- `db reset --remote` не запускается никогда: команда стирает удалённую базу.
- Seed на production не применяется: тестовые данные в рабочей базе — это потерянные реальные данные.
- Схема production меняется только миграцией, прошедшей локальную среду и `main`.
- Перед рискованной миграцией (удаление колонки, переименование, смена типа) — прогон на локальной копии и экспорт данных.
- Проверка изоляции двумя пользователями обязательна: пользователь A не должен видеть ни одной строки пользователя B.
