# Finance — техническая архитектура раздела

**Статус:** рабочий документ · версия 0.1  
**Связанные документы:** `requirements.md`, `data-model.md`, `../solo/technical-architecture.md`  
**Область:** пакет `packages/finance`, структура клиента, маршруты, тесты и порядок реализации раздела «Финансы».

---

## 1. Границы раздела

«Финансы» — самостоятельный домен внутри того же приложения. Общая с Solo Level инфраструктура: монорепозиторий на npm workspaces, React + Vite + TypeScript, Supabase (Auth + Postgres + RLS), дизайн-токены из `packages/app/src/styles/index.css`, оболочка `AppShell`.

Что **не** общее:

| Не общее | Почему |
| --- | --- |
| Доменный пакет | Другая модель: балансы, периоды, серии. Смешивание с XP даёт файл-помойку |
| XP, уровни, ритм, награды | Трата не приносит опыта: извращённый стимул |
| Сферы и цели | Финансы не сфера жизни в модели прогрессии |
| Журнал наград | Заменён операциями с ревизиями: двойного начисления здесь не бывает |

Зависимость направлена в одну сторону: `@solo/app` → `@solo/finance`. Пакет `@solo/finance` не импортирует React, Supabase и браузерные API. Приложение не импортирует `@solo/finance` из `@solo/domain` и наоборот — если появится общий тип денег, он выносится в отдельный маленький пакет, а не копируется.

## 2. Пакет `packages/finance`

```text
packages/
  finance/
    src/
      types.ts        типы: категория, операция, серия, базовая линия, снимок
      money.ts        копейки: сложение, форматирование «1 234,50 ₽», парсинг ввода
      balance.ts      target(D), fact(D), deviation(D), накопленное отклонение
      plan.ts         остаток плана, применение фактов, состояния плана
      series.ts       генерация вхождений, прижатие 29–31 к последнему дню месяца
      periods.ts      границы месяца, месячные ключи и диапазон по месяцам
      categories.ts   пользовательский порядок, фильтр и нормализация категорий
      snapshots.ts    закрытие месяца, догоняющее закрытие
      index.ts        публичная поверхность пакета
    test/
      money.test.ts
      balance.test.ts
      plan.test.ts
      series.test.ts
      periods.test.ts
      categories.test.ts
      snapshots.test.ts
```

Правила пакета те же, что у `@solo/domain`:

- чистые функции без побочных эффектов, без работы со временем «изнутри» — `today` передаётся аргументом;
- тесты на встроенном `node:test`, запуск `node --test "test/**/*.test.ts"`;
- никаких зависимостей, кроме стандартной библиотеки.

### 2.1. Публичная поверхность

Пакет экспортирует функции, а не внутренние структуры. Минимальный набор:

```ts
// money.ts
export function formatRub(minor: number): string;
export function parseRub(input: string): number | null;

// balance.ts
export interface BalanceContext {
  readonly baseline: Baseline;
  readonly operations: readonly Operation[];
  readonly categories: readonly Category[];
  readonly lastCheckpointDate?: string;
}
export function targetBalance(ctx: BalanceContext, date: string): number;
export function actualBalance(ctx: BalanceContext, date: string): number;
export function deviationAt(ctx: BalanceContext, date: string): number;
export function accumulatedDeviation(ctx: BalanceContext, snapshots: readonly Snapshot[]): number;

// series.ts
export function occurrences(series: Series, until: string): string[];

// plan.ts
export interface PlanState { status: PlanStatus; remainingMinor: number }
export function planState(plan: Operation, linkedFacts: readonly Operation[]): PlanState;

// periods.ts
export function monthKey(date: string, timezone: string): string;
export function monthBounds(monthKey: string): { start: string; end: string };
```

Точные сигнатуры уточняются при реализации; ограничение — не отдавать наружу изменяемые структуры и не давать клиенту считать деньги самостоятельно по своим формулам.

### 2.2. Что покрывается тестами

Тесты фиксируют именно те числа, что зафиксированы в документах, чтобы текст и код не расходились:

| Тест | Числа из документа |
| --- | --- |
| `balance.test.ts` | Пример §3.3 `requirements.md`: план 100/30, факт 40 → target 70, fact 60, deviation −10 |
| `balance.test.ts` | Экономия: факт 25 → fact 75, deviation +5, деньги остаются в балансе |
| `balance.test.ts` | Skipped-план исключается из target, остальные статусы входят |
| `plan.test.ts` | Остаток плана 10 − 4 = 6 при частичном исполнении; при экономии остаток не создаёт долга |
| `series.test.ts` | 12 вхождений по числу повторов; серия до 31-го числа в феврале даёт 28/29-е |
| `periods.test.ts` | Месяц закрывается по часовому поясу пользователя, а не по UTC |
| `categories.test.ts` | Порядок категорий не меняет состав и расчёты; архив отделён от активных; диапазон месяцев переставляет границы |
| `snapshots.test.ts` | Догоняющее закрытие трёх месяцев подряд; повторное закрытие меняет те же числа |

Правило проекта: любое число, попадающее в документ, получается запуском кода, а не набирается руками (`AGENTS.md` §9).

```text

      CashflowChart.tsx     две линии, выбор дня мышью и с клавиатуры, панель дня
      PlanFactList.tsx      категории за месяц, раскрытие, строка «сверх плана»
      ConfirmQueue.tsx      «подтвердить / изменить / не было»
      OperationForm.tsx     общая форма плана и факта
      MoneyInput.tsx        ввод рублей с копейками

    data/
```

Экраны — тонкий слой: считают только то, что относится к отображению (форматирование, порядок сортировки), а баланс и состояния плана берут из `@solo/finance`.

### 3.2. Маршруты и навигация

Второй пункт меню после «Сегодня» либо пятый после «Настройки» — вопрос вкуса, решение ниже. Маршруты:

| Маршрут | Экран |
| --- | --- |
| `/finance` | Обзор |
| `/finance/calendar` | Календарь |
| `/finance/operations` | Операции |
| `/finance/settings` | Настройки раздела |

В `navigation.ts` добавляется `{ path: "/finance", label: "Финансы" }`. **Решено: пятым пунктом**, после «Настроек». Причина: «Сегодня», «Прогресс», «Сферы», «Настройки» — цельный продукт про развитие; финансы — отдельное направление, и вклинивание в середину разрывает первый блок и создаёт ложную связь с геймификацией.

### 3.3. Состояние экрана

- Данные месяца загружаются одним запросом операций по диапазону дат плюс категории и действующую базовую линию; расчёт — в памяти.
- Оптимистичный отклик разрешён для подтверждения плана, но итог берётся из ответа базы.
- Ошибка записи откатывает оптимистичное значение и показывает текст ошибки, а не молчит.
- Пустые состояния: «нет операций в этом месяце» с одной кнопкой добавления; «раздел не настроен» ведёт на онбординг стартовой суммы.

### 3.4. График

Две линии по дням видимого диапазона. Требования:

- факт — сплошная линия до сегодняшнего дня, план — вторичным цветом/пунктиром на всём диапазоне;
- зум и прокрутка по дням, чтобы линия «по плановым операциям» читалась в масштабе недели;
- нулевая линия подписана, отрицательная область визуально отделена;
- точка минимума подписана датой: «минимум 12 ноября» — это и есть ответ «вниз или вверх»;
- при включённом режиме «без оценок» цвет линий нейтральный, красный не используется.

Реализация — SVG без сторонней библиотеки графиков. Причина: нужны две линии, зум и подписи; библиотека чартов приносит больше веса, чем весь раздел, а стилистика всё равно задаётся токенами. Если появится потребность в сложных видах, решение пересматривается.

### 3.5. Первый запуск

Три шага, один раз: стартовая сумма, дата отсчёта, набор категорий по умолчанию. Всё редактируемо. Без стартовой суммы нет базы для целевой линии, и первое число показывало бы «0 ₽» при реальных деньгах на руках.

### 3.6. Маскирование сумм при неактивности

`privacy.tsx` держит две вещи: контекст «суммы скрыты» и хук `useInactivityMask`, который взводит таймер на 30 секунд (`AMOUNT_MASK_DELAY_MS`) и сбрасывает его на `mousemove` и `keydown`. Провайдер стоит в `FinanceSection`, поэтому контекст покрывает все вложенные экраны и диалоги; при уходе из раздела он размонтируется и маска сбрасывается.

Компоненты `Money` и `SignedMoney` читают контекст и вместо значения показывают `••• ₽`; это же делают подписи графика и содержимое `<title>` у точек. Маскирование на уровне компонента, а не CSS-размытия: скрытое число не остаётся в DOM и не читается скринридером (для него добавлен текст «Сумма скрыта»). Поля ввода не маскируются — см. `requirements.md` §8.5.

Правило при добавлении новых мест с суммами: не вызывать `formatRub` напрямую в JSX, а использовать `Money`/`SignedMoney` или `useAmountsMasked`. Иначе новое число переживёт маскирование и станет утечкой.

## 4. Взаимодействие с базой

Чтение — обычные выборки с фильтром по `user_id` и диапазону дат. Запись:

| Действие | Как | Почему |
| --- | --- | --- |
| Создание и правка операции | Прямая вставка/обновление | Одна строка, ревизии пишет триггер |
| Подтверждение плана | `finance_confirm_plan` | Две записи в одной транзакции: факт и статус плана |
| Генерация серии | Вставка серии и набора плановых вхождений | Идемпотентна уникальным ключом; при сбое серия остаётся, вхождения можно догенерировать |
| Правка «это и все следующие» | Обновление будущих вхождений | Прошлые не переписываются никогда |
| Удаление серии | `finance_delete_series` | Прямой `delete` оставил бы сирот |
| Закрытие месяца | `finance_close_month` | Считает снимок из истории, не из клиента |
| Сброс раздела | `finance_reset` | Удаляет все данные пользователя, включая защищённые таблицы |
| Сброс раздела | `finance_reset` | Удаляет все данные пользователя, включая неизменяемые базовые линии и снимки |

Подтверждение и закрытие месяца — функции базы, а не набор запросов из браузера. Причина та же, что в Solo Level: сбой на середине оставит неполное состояние, а два быстрых нажатия создадут два факта. Инварианты (уникальность, запрет правки ревизий, ссылки) остаются в базе — там, где их нельзя обойти.

Одна формула всё же продублирована в SQL: `finance_close_month` считает цель и факт на конец месяца сам, потому что снимок закрытого месяца не должен зависеть от доверенного клиента. Это осознанное исключение; для отображения балансов и отклонений источником остаётся `@solo/finance`, а снимок после закрытия не пересчитывается. Полное описание — `../database/finance-schema.md`, §11.

## 5. Обучающий онбординг

Раздел содержит встроенное обучение — последовательность карточек, объясняющих функции шаг за шагом.

```text
packages/app/src/app/finance/tour/
  tourSteps.ts     содержание шагов; два набора: до настройки и после
  TourArt.tsx      анимированная SVG-иллюстрация к каждому шагу
  TourOverlay.tsx  карточка, подсветка элемента, перетаскивание, навигация
```

**Устройство.** Каждый шаг содержит заголовок, объяснение, список уточнений, иллюстрацию и — необязательно — привязку к экрану (маршрут) и к элементу (`data-tour="..."`). Если привязка есть, приложение переходит на нужный маршрут, прокручивает элемент в видимую область и подсвечивает его «вырезом» в затемнении.

**Выбор места карточки.** Позиция не задаётся в шаге: она вычисляется из геометрии подсвеченного блока и окна. Карточка не должна накрывать вырез — иначе подсветка теряет смысл. Порядок попыток:

| Шаг | Когда срабатывает | Что делает |
| --- | --- | --- |
| 1. Свободная сторона | Вокруг блока есть место ≥ 300 px по высоте (снизу/сверху) или ≥ 300 px по ширине (слева/справа) | Ставит карточку с зазором 16 px, при равенстве перекрытия выбирает сторону по размеру блока: у крупных — боковые, у мелких — снизу/сверху |
| 2. Компактный вид | Места нет ни с одной стороны | Убирает иллюстрацию, карточка становится ниже на ~100 px, попытка 1 повторяется |
| 3. Укороченная подсветка | Блок выше экрана целиком (календарь, список категорий) | Подсвечивает верхнюю часть блока высотой `экран − карточка − отступы`, карточка встаёт под ней |
| 4. Тесная карточка | Экран мал или масштаб страницы крупный | Оставляет полную подсветку, но разрешает карточке высоту от 140 px с внутренней прокруткой |
| 5. Без выреза | Не помогло и это | Прячет вырез, ставит карточку по центру: подсветки нет, значит и перекрывать нечего |

Причина такой иерархии: у требования «не перекрывать подсветку» приоритет выше декоративности. Иллюстрация, полная высота и вырез — по убыванию важности; подсветка сохраняется до тех пор, пока карточка читается. Компактный режим привязан к конкретной геометрии блока и сбрасывается при прокрутке или смене шага, чтобы обычная карточка не оставалась «урезанной» на новом шаге.

**Поведение, которое является требованием, а не украшением:**

| Свойство | Почему так |
| --- | --- |
| Карточку можно перетащить за любую неинтерактивную область | Подсвеченный элемент может оказаться в неудобном месте; жёсткая позиция заставляет читать сквозь преграду |
| Затенение и карточка не блокируют прокрутку страницы | Обучение объясняет экран, а экран нужно листать, чтобы увидеть объясняемое |
| `overflow: hidden` на `body` не ставится | Блокировка прокрутки — самая частая причина «обучение застряло» |
| Карточка не перекрывает вырез ни на одном шаге и ни при одном проверенном размере окна | Проверено замерами карточки и рамки в браузере: 1024×768, 1280×800, 1440×900, 1920×1080 при масштабе 100%, 125%, 150% и 200% — перекрытие 0% |
| Карточка ограничена видимой областью, координаты считаются в визуальных пикселях и переводятся в layout-пиксели | Работает при зуме страницы и на узких экранах: ширина 280–424 px, при нехватке места появляется внутренняя прокрутка текста, кнопки всегда видны; рамка и вырез совпадают с блоком при масштабе до 200% |
| Подсветка обновляется напрямую в DOM на событии `scroll`, без перерисовки React и без CSS-перехода | Иначе рамка «догоняет» страницу с задержкой и выглядит как зависание скролла; здесь расхождение с элементом — 0 px в каждом кадре |
| Затемнение — отдельный слой, а «вырез» делается его `clip-path`, а не тенью рамки | Затемнение не зависит от видимости подсвеченного блока: если блок ушёл за экран, вырез просто исчезает, а фон остаётся затемнённым |
| Позиция рамки и позиция карточки обновляются раздельно | Карточка переезжает к новому элементу с анимацией только при смене шага и ресайзе; во время прокрутки двигается одна рамка |
| При прокрутке карточка пересчитывается немедленно, если блок на неё «наехал» | Иначе подсветка перекрыта до остановки скролла; в остальных случаях карточка остаётся на месте, чтобы не дёргалась |
| Шаг сбрасывает ручную позицию | Иначе после перетаскивания следующая карточка открывается не там, где нужно |

Проверка этих свойств автоматизирована: `packages/app/tests/tour.spec.ts` проходит все шаги и на каждом сверяет геометрию карточки и рамки — карточка внутри окна и перекрытие выреза меньше 1%.

**Запуск.** До первого шага раздел показывает обучение сам (флаг `solo.finance.tour.seen.v1` в локальном хранилище). Кнопка «Обучение» в шапке раздела и «Повторить обучение» в блоке «Данные» позволяют пройти его заново. Привязка к признаку «новый пользователь» появится, когда у раздела будет серверный профиль: флаг переедет в `finance_settings`, а интерфейс не изменится.

**Навигация.** Стрелки влево/вправо, `Esc` — закрыть, кнопки «Назад» / «Далее», точки-индикаторы. Анимации — CSS-кейфреймы `tour-*` в `src/styles/index.css`; при `prefers-reduced-motion` они отключаются общим правилом проекта.

## 6. Порядок реализации

```text
1. packages/finance + тесты на числа из requirements.md §3.3
2. Домен: серии, состояние плана, снимки месяцев
3. Миграции: таблицы, триггеры, индексы, RLS, seed категорий

9. Блок «план/факт» и плашка подтверждений
10. «Принять реальность», режим «без оценок», экспорт JSON
11. Догфудинг: месяц реального учёта
```

Каждый шаг заканчивается проверяемым результатом: 1 — зелёные тесты; 2 — закрытие месяца на синтетических данных; 3 — `supabase db reset` применяет схему с нуля и отвергает неверные записи; 4 — пользователь A не видит строк пользователя B; 5 — повторное подтверждение не создаёт второй факт; 6 — число на экране совпадает с ручным расчётом по примеру документов; 11 — раздел открывается ежедневно без отвращения.

## 7. Решения, которые следуют из этой архитектуры

1. Домен пишется и тестируется до интерфейса и до подключения базы: ошибка в балансе дороже ошибки в вёрстке.
2. Финансы не делят пакет с прогрессией — разная модель, разные инварианты.
3. Клиент не считает деньги своими формулами: иначе появятся два расчёта, которые разойдутся.
4. Всё, что можно посчитать, не хранится: хранится история и точки отсчёта.
5. Изоляция данных проверяется рано и отдельно: это финансовые данные.
6. Раздел не даёт советов без нажатия и не блокирует действия — это следует из продуктового тона.

## 8. Открытые технические вопросы

1. **Импорт JSON** — нужен ли в первой версии. Рекомендация: выгрузка сейчас, импорт при первом реальном восстановлении.
2. **Проверка `today`** — откуда берётся: из часового пояса профиля. Нужно решить, что считается «сегодня» при поездке в другой пояс: местная дата устройства или дата пояса профиля. Предложение: пояс профиля, как в периодах Solo Level, чтобы месяц закрывался в одном поясе.
3. **Закрытие месяца без открытия приложения** — догоняющее закрытие при входе (текущее предложение) против запланированной серверной задачи. Для одного пользователя первое достаточно и не требует планировщика.
4. **Правка курса серии** уже после генерации вхождений: пересчитывать будущие даты или оставлять сгенерированные и менять только будущие. Предложение: пересчитывать ещё не подтверждённые вхождения, остальные не трогать.
