# Solo Level — система прогрессии

**Статус:** рабочий документ · версия 0.3  
**Связанная основа:** `product-foundation.md`  
**Платформа:** веб-приложение в браузере (основной сценарий — компьютер); вся логика этого документа платформо-независима  
**Терминология:** все пользовательские названия ниже — рабочие нейтральные плейсхолдеры. Любые термины, совпадающие с защищённым словарём франшизы, помечены как требующие замены (см. §3.1).

## 1. Задача системы

Система прогрессии должна превращать выполненные в реальности действия в понятный, устойчивый и эмоционально заметный рост. Она не оценивает ценность человека и не должна вынуждать его оптимизировать очки вместо жизни.

Критерий качества: пользователь в любой момент понимает, **за что** получил опыт, **сколько** ему осталось до следующей вехи и **какое реальное действие** приблизит его к ней.

## 2. Состав прогрессии MVP

```text
Выполнение задачи или привычки
            ↓
        запись действия
            ↓
       базовый XP + бонусы
            ↓
 ┌──────────┴───────────┐
 ↓                      ↓
Общий уровень      Сфера развития
 ↓                      ↓
Ступень / визуал   Уровень сферы + вклад
```

В MVP существуют четыре вида прогресса:

| Вид | Что показывает | Меняется от |
| --- | --- | --- |
| **Общий XP** | Совокупность вложенных усилий | Выполнений и редких достижений |
| **Общий уровень** | Долгосрочную игровую траекторию | Накопления общего XP |
| **Уровень сферы** | Куда пользователь направляет энергию и где растёт | Накопления XP, отнесённого к сфере |
| **Ритм привычки** | Насколько устойчива регулярная практика | Выполнения целевых периодов |

Валюта одна — общий XP. Уровень сферы не начисляется отдельно: это производная от вклада в сферу, считаемая по более мягкой кривой (§8.3). Обязательных «статов» у сфер нет: уровни показывают профиль направлений, а не превращают приложение в панель характеристик.

## 3. Словарь

| Термин | Значение |
| --- | --- |
| **XP** | Накопительный опыт за подтверждённые действия |
| **Общий уровень** | Веха общего прогресса, достигнутая по сумме всего XP |
| **Уровень сферы** | Веха прогресса внутри одной сферы, производная от её вклада |
| **Ступень** | Редкая визуальная веха, объединяющая несколько уровней (рабочее слово; ранее — «ранг») |
| **Сфера** | Пользовательская область развития: например, «Здоровье» или «Навык» |
| **Задача** | Пользовательское представление разового действия |
| **Ритм** | Доля успешно закрытых периодов привычки за выбранное окно наблюдения |
| **Серия** | Количество подряд успешно закрытых периодов привычки; вторичный, необязательный показатель |
| **Веха цели** | Отдельно сформулированный значимый шаг к цели |

### 3.1. Термины, требующие замены

По итогам проверки ИС (см. основу, §6) из пользовательского языка исключаются слова, прямо совпадающие с защищённым словарём франшизы. Кандидаты на замену в текущих черновиках:

| Текущее рабочее слово | Проблема | Требование к замене |
| --- | --- | --- |
| «Пробуждённый» (ступень) | Центральный термин франшизы (awakening / awakened) | Нейтральное название верхней ступени без мифологии источника |
| «Пробуждение» | То же | Не использовать |
| «Ранг S / E» и буквенные ранги | Узнаваемая шкала источника | Заменить на уровневые диапазоны или словесные ступени |

Общая RPG-лексика (уровень, опыт, задача, ступень, серия, веха) остаётся свободной и не требует замены.

Финальные названия выбираются после работы над tone of voice. Внутренняя логика не должна зависеть от конкретных терминов: в коде используются технические идентификаторы, а не отображаемые строки.

## 4. Модель данных и принцип неизменяемого журнала

Источник истины для прогрессии — **журнал наград** (`Reward Ledger`), а не число XP, сохранённое на карточке задачи.

Для каждого начисления система хранит:

| Поле | Назначение |
| --- | --- |
| `id` | Уникальный идентификатор записи |
| `occurredAt` | Когда действие было подтверждено |
| `sourceType` / `sourceId` | Задача, привычка или достижение-источник |
| `eventType` | Базовый опыт, бонус ритма, разблокировка и т. п. |
| `baseXP`, `bonusXP`, `totalXP` | Разложение награды |
| `sphereId` | Сфера, которой засчитывается опыт; может отсутствовать |
| `periodKey` | Идентификатор периода, за который засчитано выполнение (например, `2026-10-28` или `2026-W44`) |
| `idempotencyKey` | Ключ, запрещающий двойное начисление за один и тот же факт |
| `ruleVersion` | Версия правил расчёта |
| `reversesId` | Для компенсирующей записи — ссылка на отменяемую запись |

**Журнал строго append-only.** Записи никогда не изменяются и не удаляются. Отмена выполнения создаёт новую запись с отрицательным `totalXP` и заполненным `reversesId`; исходная запись остаётся неизменной. Ссылка «вперёд» (`reversedBy`) не хранится в исходной записи, потому что это было бы изменением истории; отменённость выводится поиском компенсирующей записи по `reversesId`.

**Идемпотентность обязательна.** Ключ строится детерминированно из источника и периода: `sourceType + sourceId + periodKey + eventType`. Повторная отправка формы, повтор операции после сбоя, повторный импорт резервной копии и правка задним числом (см. §9.3) не должны создавать вторую награду. Итоговые значения XP, уровня и ритма всегда вычисляются из журнала, а не хранятся как отдельный источник истины.

Зачем это нужно: журнал оправдан **отменой действий, правкой задним числом, аудитом ошибок, сменой формул между версиями, переносимым экспортом данных и корректной многопользовательской синхронизацией**. С переходом на сервер и реляционную БД (см. технический документ) журнал становится ещё важнее: несколько устройств могут отправить подтверждение одновременно, и единственный способ свести это без двойного начисления — детерминированный ключ идемпотентности плюс неизменяемая история, а не перезапись счётчика.

Пользовательский интерфейс показывает итог, но не обязан раскрывать технический журнал.

## 5. Базовый опыт

### 5.1. Шкала усилия

При создании задачи или привычки пользователь выбирает не «сложность личности», а ожидаемый объём одного выполнения. По умолчанию предлагается средний вариант.

| Уровень усилия | Подсказка | Базовый XP | Примеры |
| --- | --- | ---: | --- |
| 1 — короткий шаг | до 10 минут | 10 | разобрать один документ, 5 минут растяжки |
| 2 — лёгкая сессия | 10–25 минут | 20 | прогулка, повторить слова |
| 3 — обычная сессия | 25–60 минут | 35 | тренировка, учебный блок |
| 4 — глубокая работа | 1–2 часа | 55 | важный рабочий этап, практика навыка |
| 5 — большая веха | более 2 часов или высокий фокус | 80 | экзамен, крупный этап проекта |

Шкала намеренно не линейная: 80 XP за большой шаг ощутимы, но пять коротких полезных дел по-прежнему сопоставимы с одной большой сессией.

### 5.2. Кто задаёт усилие

- уровень усилия задаётся при планировании, а не в момент получения награды;
- его можно изменить до выполнения без штрафа;
- после выполнения изменение требует отменить выполнение и подтвердить его заново;
- шаблоны предлагают разумное значение, но никогда не утверждают, что одна категория жизни объективно важнее другой.

Такой порядок снижает соблазн повышать сложность только ради опыта, сохраняя гибкость при неверной оценке времени.

### 5.3. Особенности задач

Разовая задача даёт базовый XP один раз. Если действие повторяется, оно моделируется привычкой или серией отдельных задач, а не многократным нажатием «выполнить» на одной карточке.

### 5.4. Особенности привычек

Одно допустимое выполнение привычки за один запланированный период даёт базовый XP. Дополнительные отметки в тот же период можно сохранить в журнале как личную статистику, но XP не добавляются.

**Период** зависит от расписания:

| Расписание | Период | Пример `periodKey` |
| --- | --- | --- |
| Каждый день | Календарный день в часовом поясе пользователя | `2026-10-28` |
| Выбранные дни недели | Конкретный день недели | `2026-10-28` |
| N раз в неделю | Неделя от локального начала недели | `2026-W44` |
| N раз в месяц | Календарный месяц | `2026-10` |

Это делает правила предсказуемыми для пользователя, который тренируется три раза в неделю или читает несколько раз в месяц.

### 5.5. Периоды, часовые пояса и идентичность периода

`periodKey` вычисляется один раз в момент подтверждения и **сохраняется в записи журнала, а не пересчитывается при чтении.** Причина: часовой пояс пользователя может измениться (перелёт, перевод часов), и пересчёт задним числом разложил бы одну и ту же историю в разные периоды при каждом открытии приложения.

Следствия:

- **часовой пояс — часть настроек, а не часть записи.** Записи хранят свой `periodKey` и `occurredAt`; при смене пояса старые записи не пересчитываются;
- **начало дня** задаётся настройкой (по умолчанию — 04:00 локального времени, а не полночь), чтобы вечерние отметки после полуночи не разрывали логический день;
- **начало недели** задаётся настройкой (§5.4) и тоже фиксируется в момент записи;
- для привычек «N раз в неделю» ожидаемое число периодов равно `N` в каждую неделю, включая недели с пропусками: ритм считает не «сколько раз получилось», а «сколько периодов закрыто из ожидаемых»;
- переход на летнее время не влияет на `periodKey`, потому что он строится по локальному календарю, а не по количеству прошедших часов.

## 6. Бонусы

Бонусы должны быть редкими, объяснимыми и не должны превращать приложение в задачу по оптимизации коэффициентов.

### 6.1. Бонус первого шага — +5 XP

Начисляется один раз, когда пользователь впервые завершает действие в новой сфере. Награда подчёркивает начало пути, но слишком мала, чтобы создавать стимул искусственно плодить сферы.

### 6.2. Бонус ритма привычки — до +20% базового XP

Начисляется за выполнение привычки при высоком ритме. **Окно расчёта — до 4 последних ожидаемых периодов строго до закрываемого, ограниченное датой создания привычки.** Только что закрытый период в окно не входит: награда за шаг не должна зависеть от того, посчитан ли этот шаг уже в показателе.

| Ритм за предыдущие периоды | Бонус |
| --- | ---: |
| 0–25% | 0% |
| 50% | +5% |
| 75% | +10% |
| 100% | +20% |

Промежуточные значения округляются до ближайшей ступени таблицы вниз.

**Этап настройки.** Бонус не начисляется, пока у привычки меньше трёх уже прошедших ожидаемых периодов. Без этого правила первая же повторная отметка давала бы 1/1 = 100% и максимальный бонус за один день практики.

| Выполнение | История в окне | Ритм | Бонус |
| ---: | --- | ---: | ---: |
| 1-е | 0 периодов | — | 0% |
| 2-е | 1 период | этап настройки | 0% |
| 3-е | 2 периода | этап настройки | 0% |
| 4-е | 3 периода | 100% при трёх успешных | +20% |
| 5-е | 4 периода | 100% при четырёх успешных | +20% |

Бонус оценивает регулярность, а не длину календарной серии: одна пропущенная тренировка не обесценивает несколько недель работы.

**Разные расписания — разная цена «этапа настройки».** Привычка «каждый день» проходит этап настройки за 3 дня, привычка «3 раза в неделю» — за полторы недели, привычка «1 раз в месяц» — за три месяца. Чтобы бонус не был недоступен месяцами, для привычек с редким расписанием окно дополнительно ограничено календарём: **не более 28 дней назад**. Для месячных привычек это означает, что в окно попадают ожидаемые периоды за последние 4 недели, а не за последние 4 месяца.

### 6.3. Веха цели — разовая надбавка за завершение

Веха — отдельный подготовленный шаг к цели с оценкой усилия 3, 4 или 5. Примеры: «собрать портфолио из трёх кейсов», «пробежать первые 5 км», «сдать экзамен».

Механика вехи переработана относительно версии 0.1, где веха давала фиксированные 30 / 55 / 80 XP. Это делало крупную веху экономически хуже обычной задачи того же усилия (усилие 3: веха 30 XP против задачи 35 XP) и противоречило смыслу вехи как долгой работы.

Правила версии 0.2:

- **веха — это контейнер, а не источник XP.** К вехе можно привязать задачи и привычки, и они начисляют опыт как обычно, по общим правилам §5;
- закрытие вехи даёт **разовую надбавку +25% от суммы XP, фактически начисленной по привязанным к ней действиям**, но не более 300 XP и не менее 15 XP;
- надбавка начисляется один раз, при ручном подтверждении завершения вехи, и не заменяет опыт вложенных действий;
- веха без привязанных действий по-прежнему допустима как разовое крупное действие: тогда её база — XP усилия 3/4/5 по §5.1, надбавка не начисляется.

Так веха «три месяца работы» перестаёт конкурировать с одной тренировкой: она возвращает процент от реально вложенного усилия, а не фиксированную сумму.

### 6.4. Чего в MVP нет

- случайных множителей;
- ежедневного бонуса за вход;
- платных бустеров;
- штрафов или отрицательного XP за пропуск;
- бонусов за количество проведённого в приложении времени;
- бонусов за количество созданных сущностей (сфер, вех, привычек).

## 7. Уровни

### 7.1. Формула

Для перехода с уровня `L` на `L + 1` требуется:

```text
XPNext(L) = round(100 × 1.05^(L − 1))
```

где первый уровень начинается с 0 XP, а первый переход (1 → 2) требует 100 XP.

**Коэффициент снижен с 1.12 до 1.05 по итогам расчёта.** Версия 0.1 с `1.12` давала вырожденную кривую в долгую: уровень 55 наступал на 7 562-й день при 50 XP/день (свыше 20 лет), а один уровень на отметке 55 требовал 45 475 XP, то есть около 909 активных дней. Это делало верхние ступени недостижимыми и противоречило требованию §7.2 «не потерять ценность спустя несколько месяцев».

Накопительный опыт, требуемый для достижения уровня `N`, равен сумме `XPNext(1)` … `XPNext(N − 1)`.

### 7.2. Ожидаемый темп

Ориентир — 40–60 XP за активный день; в таблице ниже использовано 50 XP/день.

| Веха | Накопительный XP `1.12` (v0.1) | Накопительный XP `1.05` (v0.2) | Время при 50 XP/день (v0.2) |
| --- | ---: | ---: | --- |
| Уровень 2 | 100 | 100 | 2 дня |
| Уровень 5 | 477 | 431 | 9 дней |
| Уровень 10 | 1 476 | 1 104 | ~22 дня |
| Уровень 20 | 6 343 | 3 056 | ~61 день |
| Уровень 35 | 38 450 | 8 510 | ~170 дней |
| Уровень 55 | 378 124 | 25 880 | ~518 дней |

*Числа этого раздела получены запуском `npm run gen:progression` (правило происхождения чисел, `AGENTS.md`). Ранее в таблице стояло редуцированное значение `477` для уровня 5, не соответствовавшее ни одной из кривых: это была ошибка переноса.*

Целевой коридор: первые уровни появляются ежедневно-через день, десятый — в течение первого месяца, верхняя ступень — примерно через 17 месяцев регулярной практики. Это стартовая балансная гипотеза; коэффициент корректируется по фактическому темпу догфудинга. Формула и все числа этого раздела платформо-независимы и должны быть покрыты тестами до разработки интерфейса.

**Важное следствие для дизайна:** при `1.05` форма кривой в первые две недели почти совпадает с `1.12`, поэтому раннее ощущение прогресса не меняется. Меняется только хвост — и именно он был нерабочим.

### 7.3. Ступени

Ступень — более редкая и визуально выразительная веха, привязанная к диапазону уровней. Все названия ниже — рабочие плейсхолдеры, подлежащие замене (§3.1):

| Ступень | Уровни | Начало ступени при 50 XP/день | Длительность ступени |
| --- | --- | --- | --- |
| Начало пути | 1–9 | день 0 | ~3 недели |
| Разгон | 10–19 | ~3 неделя | ~1,5 месяца |
| Устойчивость | 20–34 | ~2 месяца | ~3,5 месяца |
| Мастер практики | 35–54 | ~5,5 месяцев | ~11 месяцев |
| Вершина | 55+ | ~17 месяцев | — |

Ориентиры рассчитаны по кривой `1.05` при 50 XP/день и подлежат пересчёту при изменении коэффициента.

Все пять ступеней достижимы внутри одной траектории догфудинга при коэффициенте `1.05`; при `1.12` четыре из пяти были недостижимы. Названия «Пробуждённый» и «Проводник» из версии 0.1 удалены как совпадающие со словарём франшизы.

При росте ступени открывается крупная визуальная веха. В версии 0.2 это **не обязательно персонаж**: ступень открывает тему оформления интерфейса (палитра, форма панелей, звук подтверждения, эмблема ступени). Обычный уровень даёт меньшие сигналы — прогресс-бар, краткую анимацию, запись в истории.

### 7.4. Необратимость прогресса

Полученный за честно выполненное действие XP не исчезает из-за пропуска, паузы или изменения расписания. Уменьшение возможно только при явной отмене ошибочно подтверждённого выполнения. Уровень может снизиться только как следствие такой отмены; это должно быть заметно и подтверждено пользователем.

### 7.5. Смена формулы и сохранение уровня

`ruleVersion` на записи журнала защищает **начисление**: старая запись навсегда хранит свой `totalXP`. Но уровень — функция от суммы XP, поэтому смена коэффициента меняет и уровень, что нарушает §14 в версии 0.1.

Правило версии 0.2:

- уровень вычисляется по кривой текущей версии правил (**`levelCurveVersion` — отдельная настройка**, не равная `ruleVersion` записи);
- при смене кривой пользователю показывается предварительный расчёт: «было 24, станет 26» и явное подтверждение;
- после подтверждения сохраняется `curveMigration` — запись о переходе, чтобы уровень не «прыгал» туда-обратно и объяснение изменения осталось в истории;
- XP никогда не пересчитывается задним числом: миграция касается только отображения уровня.

## 8. Сферы развития

### 8.1. Стартовый набор

В онбординге приложение предлагает **три** нейтральные сферы, которые можно переименовать, удалить или дополнить: **Здоровье**, **Разум**, **Ремесло**.

Остальные сферы доступны для добавления вручную, если пользователь захочет расширить систему:

| Сфера | Что покрывает |
| --- | --- |
| Здоровье | сон, движение, питание, режим |
| Разум | обучение, чтение, мышление |
| Ремесло | работа, карьера, личные проекты |
| Связи | отношения, семья, сообщество |
| Опора | быт, финансы, восстановление |

«Сфера» не ранжирует людей и не требует баланса по умолчанию. Пользователь может сознательно посвятить сезон одной области.

### 8.2. Распределение XP

Весь `totalXP` завершённого действия зачисляется в общий XP; тот же объём отображается как вклад в одну выбранную сферу. Это не двойное начисление — два представления одной и той же награды.

Действия без сферы учитываются только в общем прогрессе. В аналитике они отображаются как «без направления», чтобы пользователь мог исправить систему, если это важно.

### 8.3. Уровни сфер

У каждой сферы есть собственный уровень, чтобы видеть, куда уходит энергия и где идёт рост. Это не отдельная валюта: **валюта одна — общий XP.** Уровень сферы — производная величина от суммы XP, зачисленного в эту сферу; отдельного начисления нет.

Связь с общим уровнем:

| | Общий уровень | Уровень сферы |
| --- | --- | --- |
| Считается от | Суммы всего XP | Суммы XP, отнесённого к сфере |
| Кривая | `1.05` (§7.1) | мягче: `1.03` |
| Действия без сферы | Учитываются | Не учитываются |
| Смысл | Долгосрочная траектория | Профиль направлений |

Кривая сфер специально мягче, иначе при делении внимания между несколькими сферами уровни сфер стояли бы почти на месте. Ориентир при общем темпе 50 XP/день:

| Доля внимания на сферу | XP/день на сферу | Уровень 5 | Уровень 10 | Уровень 20 |
| --- | ---: | --- | --- | --- |
| ~50% (одна главная) | 25 | ~17 дней | ~41 день | ~100 дней |
| ~34% (три равные) | 17 | ~25 дней | ~60 дней | ~148 дней |
| ~25% (четыре равные) | 12,5 | ~33 дня | ~81 день | ~201 день |

Числа по той же причине, что и в §7.2: это стартовая балансная гипотеза, а не обещание. Коэффициент `1.03` проверяется в догфудинге: если уровни сфер идут слишком медленно и теряют смысл, он повышается.

**Важное следствие для данных:** уровень сферы всегда выводится из журнала пересчётом, а не хранится отдельным счётчиком. Это исключает расхождение между общим XP, вкладом сферы и её уровнем.

### 8.4. Показатели сферы

В MVP сфера показывает:

- собственный уровень и прогресс до следующего;
- XP за выбранный период;
- долю от общего прогресса;
- число выполнений;
- активные цели и привычки;
- короткую динамику относительно предыдущего сопоставимого периода.

Не показываются «провалы» в красном цвете, ранжирование сфер между собой и искусственные рекомендации «срочно прокачать слабую сферу».

## 9. Привычки: ритм, серия и восстановление

### 9.1. Ритм — главный показатель

**Показатель ритма и окно бонуса разделены.** В версии 0.1 и то, и другое считалось по 4 последним периодам, из-за чего «главный показатель» для ежедневной привычки фактически измерял последние четыре дня — то есть был замаскированной серией и противоречил §9.2.

Правило версии 0.2:

| Назначение | Окно |
| --- | --- |
| **Отображаемый ритм** (главный показатель) | Скользящее окно 28 дней, ограниченное началом привычки |
| **Бонус ритма** (§6.2) | 4 предыдущих ожидаемых периода, не более 28 дней |
| **Серия** (§9.2) | Подряд успешные периоды без ограничения окна |

Отображаемый ритм считается как доля успешно закрытых ожидаемых периодов в окне:

```text
Rhythm = successfulPeriods / expectedPeriods × 100%
```

Для ежедневной привычки окно 28 дней даёт 28 периодов, поэтому один-два пропуска двигают показатель на 3–7 процентов, а не на 25. Пока привычка моложе окна, знаменатель равен числу прошедших ожидаемых периодов, а не 28: показатель не наказывает за то, что привычка только началась.

В интерфейсе его лучше показывать человеческим языком: «устойчиво», «набирает форму», «возвращаем ритм», а процент оставлять вторичным.

### 9.2. Серия — опциональный вторичный показатель

Серия равна числу последних подряд успешных периодов. Пропуск завершает текущую серию, но не удаляет рекорд, не влияет на общий XP и не меняет визуальный статус пользователя на негативный.

Серия **не участвует в расчёте награды** ни в каком виде: она не влияет ни на базовый XP, ни на бонус ритма. Это отличает её от показателя ритма и делает выключение серии в настройках безопасным для прогрессии.

Пользователь может скрыть серию из интерфейса в настройках. Никаких «заморозок серии» за оплату или давление восстановить её задним числом.

### 9.3. Отложенное выполнение

Для ежедневной привычки отметку можно поставить в течение локального дня. После полуночи период фиксируется как пропущенный. Пользователь может вручную исправить ошибку журнала в течение 48 часов, указывая фактическую дату выполнения. Это коррекция данных, а не «спасение серии».

Правка задним числом использует тот же `idempotencyKey` (§4) с фактическим `periodKey`: если за этот период награда уже была начислена, правка изменяет запись даты, а не создаёт вторую. Если период был отмечен как пропущенный, создаётся обычная запись награды с указанной датой и правилами той версии, что действует сейчас.

### 9.4. Возвращение после паузы

После 7 дней без подтверждённых действий приложение не показывает накопленный список просроченных обязательств. Вместо этого оно предлагает:

1. выбрать одно действие на сегодня или отметить уже сделанное;
2. отложить, изменить частоту либо архивировать устаревшие привычки;
3. получить обычный XP за возвращение — без штрафа и без искусственного «супер-бонуса».

Пропущенные периоды **не закрываются задним числом и не превращаются в «долг на отработку»**: они остаются фактом истории и влияют только на показатель ритма, который постепенно восстанавливается сам.

## 10. Цели и вехи

Цель отвечает на вопрос «зачем», а не является самостоятельной фабрикой XP.

### 10.1. Типы целей

| Тип | Формулировка | Как измеряется |
| --- | --- | --- |
| Результат | «Пробежать 10 км» | Числовой показатель, дата или ручное подтверждение |
| Практика | «Укрепить разговорный английский» | Набор вех и связанных привычек |
| Проект | «Подготовить портфолио» | Завершённые задачи и вехи |

Соответствие личной цели интервью («выполняю каждый день шаги и вижу, как они по кирпичику складываются в глобальную цель»): именно эту связь обеспечивают веха и один числовой индикатор цели. Это ядро продукта, а не дополнительная функция, поэтому связь «действие → веха → цель» проверяется в догфудинге наравне с основным циклом.

### 10.2. Правила связи

- задача или привычка может относиться к одной цели;
- цель содержит не более одного активного числового индикатора в MVP;
- закрытие связанного действия увеличивает прогресс цели только если пользователь явно задал вклад (например, «+1 тренировка из 12»);
- полное достижение цели выдаёт празднование и запись достижения, но не дополнительный XP: цель — контекст, а не источник награды. Опыт начисляется действиями и надбавкой за веху (§6.3), но не за сам факт «цель достигнута».

Это исключает двойное начисление и делает цели честным контекстом, а не поводом «кликнуть ради опыта».

## 11. Защита от фарма и ошибок

Задача анти-фарма — не подозревать пользователя во лжи, а не давать интерфейсу случайно поощрять пустые действия.

| Риск | Правило MVP |
| --- | --- |
| Многократное закрытие одной привычки | Одна XP-награда на плановый период |
| Дублирование одинаковых привычек | Мягкое предупреждение при совпадении названия и расписания; не блокировать |
| Повышение сложности после факта | Требуется отмена и новое подтверждение |
| Двойной XP у цели и задачи | Надбавка за веху начисляется один раз и не дублирует опыт вложенных действий |
| Массовое создание микрозадач | Нет жёсткого дневного потолка; weekly review подсвечивает долю XP от коротких шагов без осуждения |
| Случайная отметка | Undo в течение 10 секунд; позднее — безопасная отмена через журнал |
| Повторная отправка и повторный импорт | `idempotencyKey` (§4) блокирует второе начисление за тот же факт |
| Инфляция объявленного усилия | Не блокируется: пользователь не подозревается в обмане. Наблюдается как метрика — доля XP, полученная с усилием 4–5. Рост этой доли вместе с ростом скорости уровней означает, что шкала усилия требует пересмотра, а не наказания |

**Про инфляцию усилия отдельно.** Уровень усилия объявляет сам пользователь и может менять его до выполнения без штрафа (§5.2). В личном инструменте это не проблема доверия, но это проблема измеримости: без наблюдения за распределением усилий невозможно отличить «пользователь стал действовать больше» от «пользователь стал называть то же самое более крупными словами». Именно поэтому распределение усилий попадает в недельный обзор и в метрики догфудинга, а не в запреты.

Жёсткий дневной лимит XP в MVP не вводится. Он наказывает реальный продуктивный день и учит пользователя «оставлять действия на завтра». Если телеметрия покажет злоупотребление, сначала применяются прозрачные ограничения на одинаковые источники, а не общий потолок.

## 12. События и состояние после выполнения

При подтверждении действия система выполняет операции атомарно:

1. проверяет, допускает ли расписание новое засчитываемое выполнение;
2. вычисляет `idempotencyKey` и убеждается, что награда за этот факт ещё не начислена;
3. создаёт запись выполнения;
4. рассчитывает базовый XP и применимые бонусы по версии правил;
5. создаёт запись в журнале наград;
6. пересчитывает общий XP, общий уровень, уровни сфер, вклад в сферу и ритм привычки;
7. определяет, достигнуты ли уровень, ступень или визуальная разблокировка;
8. отправляет в UI единый результат награды.

Карточка результата должна занимать несколько секунд и отвечать на три вопроса:

```text
Что сделано?      «Тренировка завершена»
Что получено?     «+39 XP: 35 базовых + 4 за устойчивый ритм»
Что изменилось?   «До 12 уровня — 61 XP»
```

Если уровень повышен, карточка разворачивается в отдельный праздничный момент. Если нет — пользователь может сразу закрыть её и продолжить день.

## 13. Примеры расчёта

### Пример A: новая привычка

Пользователь создаёт ежедневную привычку «10 минут английского» с усилием 2, сферой «Разум».

- Первое выполнение: 20 базовых XP + 5 XP первого шага = **25 XP**.
- Второе и третье выполнение: по **20 XP** без бонуса — идёт этап настройки (§6.2).
- Четвёртое выполнение: история окна — три успешных периода из трёх, ритм 100%, бонус +20%, итого **24 XP**.
- Пятое и последующие выполнения при сохранении ритма 100%: **24 XP** каждое.

### Пример B: большая задача

Пользователь завершает «Подготовить первую версию резюме» с усилием 4 в сфере «Ремесло».

- Награда: **55 XP**.
- Если это первое действие пользователя в сфере «Ремесло»: ещё +5 XP, итого **60 XP**.

### Пример C: пропуск

Пользователь не выполнил ежедневную тренировку во вторник.

- Общий XP не меняется.
- Текущая серия прерывается.
- Окно бонуса (4 предыдущих периода) показывает 75%, поэтому последующий бонус составляет 10% → 21 XP при базе 20.
- **Отображаемый ритм** почти не двигается: в окне 28 дней один пропуск даёт ~96%, то есть показатель остаётся «устойчивым».
- В интерфейсе нет штрафной анимации или красного «провала».

### Пример D: веха цели

Пользователь три месяца шёл к цели «Подготовить портфолио» и привязал к вехе задачи на суммарные 620 XP.

- Надбавка за завершение вехи: 25% от 620 = 155 XP (в пределах лимита 300).
- Итого за веху: **155 XP** сверх уже полученного за задачи.
- При старой механике (фиксированные 80 XP) та же работа дала бы 80 XP, то есть в разы меньше, и веха была бы экономически невыгоднее одной тренировки.

## 14. Балансные решения, требующие теста

До публичного релиза тестируются и могут меняться:

- формула роста XP между уровнями (`1.05` — стартовая гипотеза версии 0.2; `1.12` в версии 0.1 давала вырожденный хвост кривой);
- кривая уровней сфер (`1.03` — стартовая гипотеза; сферы должны расти заметно медленнее общего уровня, но не стоять на месте);
- диапазоны базового XP и реальный субъективный вес усилий;
- окна ритма: 28 дней для показателя и 4 периода (≤28 дней) для бонуса;
- размер и момент бонуса первого шага;
- формула надбавки за веху: 25%, лимит 300 XP, минимум 15 XP;
- частота визуальных разблокировок;
- ясность терминов «ритм», «серия», «веха», «ступень» в пользовательском тексте.

Ни одно изменение правил не должно тихо менять уже выданную награду. При миграции новая формула применяется к новым выполнениям; старые записи сохраняют свою `ruleVersion`. Изменение кривой уровней обрабатывается отдельно по правилу §7.5 (подтверждаемая миграция уровня), потому что уровень зависит от суммы XP, а не от одной записи.

## 15. Решения, которые следуют из этой логики

1. Первым главным экраном становится **«Сегодня»**, а не экран прогресса: игровой слой должен следовать за реальным действием.
2. Создание сущности должно занимать меньше минуты; выбор усилия и сферы — два ключевых поля, остальное раскрывается по запросу.
3. Экран прогресса показывает общий уровень, уровни сфер, ближайшую веху и распределение по сферам; не создаёт отдельную игру с валютами.
4. Визуальные вехи строятся как путь заранее известных изменений оформления, а не как случайный набор предметов. В первой версии это темы интерфейса и эмблемы ступеней, а не персонаж.
5. Все вычисления прогрессии выполняются в отдельном модуле без зависимости от UI и от способа хранения, чтобы логику можно было покрыть тестами до появления интерфейса и перенести между платформами позже.

Следующий документ: `user-flows.md` — онбординг, «Сегодня», создание и выполнение действия, отметка сделанного, пропуск, возвращение и обзор недели (со схемами). Порядок работы и связанные документы перечислены в `product-foundation.md`, §13.
