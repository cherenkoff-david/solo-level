**Связанные документы:** `database/README.md`, `database/solo-schema.md`, `database/finance-schema.md`, `solo/technical-architecture.md` (§6, §8), `local-run.md`, `finance/data-model.md`

## 1. Среды

| Среда | Что это | Где живёт | Данные | Кто пишет |
| --- | --- | --- | --- | --- |
| **local** (test) | Полный стек Supabase в Docker на этой машине | `supabase/` в репозитории, контейнеры локально | Синтетические, можно стирать | Разработка и проверка миграций |
| **prod** | Облачный проект Supabase | Аккаунт Supabase, проект `solo` | Реальные | Только через миграции из ветки `main` |

Правило продвижения: **local → `main` → prod**, никогда наоборот. Любая миграция сначала применяется локально на чистой базе (`db:reset`), потом попадает в `main`, и только после этого CI применяет её к prod.

Почему local — тестовая среда, а не отдельный облачный проект: локальный стек бесплатный, работает без сети, его можно стирать и пересобирать сколько угодно, а ошибка в миграции не касается реальных данных. Облачный dev-проект понадобится, только если тестировать нужно именно поведение платформы (например, лимиты или засыпание проекта).

### 1.1. Что именно «переезжает» из локальной среды в прод

Приложение — **один и тот же код** в GitHub-репозитории. Прод — это не отдельная копия приложения, а та же сборка, которая смотрит на другой проект Supabase. Среду выбирает не код, а переменные окружения:

| | Локально | Прод |
| --- | --- | --- |
| Код клиента | рабочая копия из репозитория | та же ветка `main`, собранная хостингом |
| `VITE_SUPABASE_URL` | `http://127.0.0.1:54321` | `https://wtpiyygnffemrboyjlwo.supabase.co` |
| Ключ | publishable локального стека | publishable облачного проекта |
| База | контейнер Postgres на машине | Postgres в облаке |

Из локальной среды в прод едет **только схема** — SQL-файлы миграций, закоммиченные в `main`. Данные не едут никогда и ни в какую сторону:

- локальные записи живут в Docker-томе и умирают при `db:reset`; они не «уезжают» в облако;
- продовые записи не копируются на машину разработчика, иначе это была бы утечка персональных данных на ноутбук;
- `seed.sql` применяется только при локальном `db reset` — на prod сид не запускается.

Отсюда практическое следствие: если нужно посмотреть, как поведёт себя миграция на «похожих на реальные» данных, данные готовятся локально или берутся из выгрузки — но подключение к продовой базе для разработки не используется.

## 2. Что лежит в репозитории

```text
supabase/
  config.toml      настройки локального стека: порты, Auth, Mailpit, версия Postgres
  migrations/      схема; меняется только миграциями, файлы коммитятся
  seed.sql         локальные данные для db reset; на prod не применяется
```

- **CLI — dev-зависимость проекта** (`package.json`), а не глобальная установка. Причина: у всех, включая CI, одна и та же версия CLI, и команды воспроизводимы. Запуск — через `npm run db:*`.
- **`config.toml` коммитится.** Пароли и секреты в нём не хранятся: для них используется подстановка `env(...)` из `.env`.
- **`migrations/` — единственный способ менять схему.** Ручные правки через Studio не попадают в историю: следующий `db reset` их потеряет, а prod разойдётся с local.

## 3. Локальная среда

### 3.1. Требования

- Docker (Docker Desktop или OrbStack) — демон должен быть запущен;
- Node.js 22.18+ и зависимости проекта (`npm install`).

### 3.2. Команды

```bash
npm run db:start     # поднять Postgres + Auth + Studio + Mailpit
npm run db:status    # адреса, ключи, состояние контейнеров
npm run db:reset     # пересобрать локальную БД из миграций и seed (данные теряются)
npm run db:stop      # остановить контейнеры (данные сохраняются)
```

Создание миграции и проверка изменений:

```bash
npm run db:new -- add_habits     # создать пустой файл миграции
npm run db:diff -- -f my_change  # сгенерировать миграцию по правкам в Studio
```

Первый `db:start` скачивает образы (несколько минут и гигабайты). Это разовая операция; дальше запуск занимает секунды.

**Если реестр образов недоступен или тянет слишком медленно** (на этой машине так и было: Docker Hub и `public.ecr.aws` отдавали образы по несколько мегабайт в минуту), используйте официальное зеркало Supabase в GHCR:

```bash
npm run db:start:slim   # то же самое, но образы берутся из ghcr.io/supabase/cli/*
```

Зеркальные образы — это те же сервисы Supabase в облегчённой сборке. Для локальной разработки этого достаточно; отличие в том, что часть утилит внутри контейнера отсутствует, поэтому самопроверки отдельных сервисов могут ругаться — на работу БД, Auth, REST и Studio это не влияет. Не путайте это с подменой тегов вручную: перетегировать зеркальный образ под именем обычного нельзя, CLI тогда считает его обычным и падает на health-check.

### 3.3. Порты и адреса

| Что | Адрес |
| --- | --- |
| API / Auth (gateway) | `http://127.0.0.1:54321` |
| Postgres | `127.0.0.1:54322` |
| Studio (веб-интерфейс БД) | `http://127.0.0.1:54323` |
| Mailpit (перехват писем Auth) | `http://127.0.0.1:54324` |

Порты фиксированы в `config.toml`, поэтому второй локальный стек на этой же машине одновременно не запустится.

**Почта локально не отправляется.** Ссылки входа и подтверждения адреса попадают в Mailpit — удобно проверять сценарии Auth без внешней почты и без лимитов.

### 3.4. Переменные окружения клиента

```bash
cp packages/app/.env.example packages/app/.env.local
npm run db:status -- -o env    # взять URL и publishable/anon key
```

Vite читает `.env.local` из каталога пакета `packages/app/`, поэтому файл лежит там. В клиент попадают только переменные с префиксом `VITE_`; публикуемый ключ безопасен, потому что даёт ровно то, что разрешают RLS-политики. **Секретный ключ (`secret` / `service_role`) в клиент и в репозиторий не попадает никогда.**

Имена переменных: `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` — для локальной среды и для prod они одни и те же, меняются только значения. Это важно: код клиента не должен знать, с какой средой он говорит.

## 4. Production: облачный проект

Проект создан: **`Solo`**, `project-ref` = `wtpiyygnffemrboyjlwo`, регион `eu-west-3` (Париж), Postgres 17.11. Каталог связан с ним командой `npx supabase link --project-ref wtpiyygnffemrboyjlwo`; связь хранится в `supabase/.temp/` (в `.gitignore`), поэтому на другой машине связывание повторяется.

1. Войти в CLI: `npx supabase login` (откроется браузер). В неинтерактивной среде браузерный вход недоступен — тогда нужен личный токен: Dashboard → Account → Access Tokens, затем `npx supabase login --token <token>` (в git и в чат токен не попадает).
2. Связать каталог с проектом: `npx supabase link --project-ref wtpiyygnffemrboyjlwo`.
3. Применить миграции: `npx supabase db push --dry-run --remote`, затем `npx supabase db push --yes --remote`.
4. Записать в клиентское окружение хостинга `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY`.
5. В настройках Auth указать `Site URL` и разрешённые redirect-адреса реального домена. На prod подтверждение почты включено (локально по умолчанию выключено).

Пароль БД для `db push` не нужен: CLI с личным токеном создаёт себе временную служебную роль (`Initialising login role...`) и работает через неё. Пароль остаётся только в менеджере паролей как резервный доступ к базе.

**Ключи и инструкция «Connect» в панели проекта** (Dashboard → кнопка Connect) — это страница для подключения клиента: там лежат URL проекта и publishable/secret ключи. Ею пользуются, чтобы заполнить `.env`, но она не заменяет `supabase link`: связывание нужно CLI и CI, чтобы применять миграции. Это разные задачи: ключи — доступ к данным через API, `link` — право менять схему.

Проверка: `npx supabase migration list --remote` показывает по колонкам Local/Remote, какие миграции применены где.

### 4.1. Чего нельзя делать с настройками prod

`config.toml` описывает **локальную** среду: `site_url = http://127.0.0.1:3000`, подтверждение почты выключено, OTP из 6 цифр. Команда `supabase config push` перенесла бы эти значения на prod и, например, отключила бы подтверждение почты в рабочем приложении. Поэтому:

- `supabase config push` из этого репозитория на prod **не запускается**;
- настройки Auth на prod меняются в панели проекта, руками;
- перед любой командой, которая трогает удалённый проект, полезно посмотреть `supabase config diff` — он показывает построчно, что изменилось бы.

## 5. CI: `main` — это production

Файл `.github/workflows/db-prod.yml` применяет миграции к prod при push в `main`, если менялись файлы `supabase/migrations/` (или сам файл workflow — это позволяет проверить цепочку первым push). Секреты заданы на уровне репозитория `cherenkoff-david/solo-level`:

| Секрет | Что это |
| --- | --- |
| `SUPABASE_ACCESS_TOKEN` | Личный токен доступа Supabase (Dashboard → Account → Access Tokens) |
| `SUPABASE_PROJECT_ID` | `wtpiyygnffemrboyjlwo` |

Править их: GitHub → вкладка **Settings** репозитория → в левом меню **Secrets and variables** → **Actions**. Если пункта нет — значит, открыт не тот экран: он существует только у репозитория, где у аккаунта есть права администратора, и только во вкладке репозитория, а не в настройках аккаунта. Через CLI то же самое делается без браузера:

```bash
gh secret set SUPABASE_ACCESS_TOKEN --repo cherenkoff-david/solo-level   # значение вводится скрыто
gh secret set SUPABASE_PROJECT_ID --repo cherenkoff-david/solo-level     # wtpiyygnffemrboyjlwo
gh secret list --repo cherenkoff-david/solo-level                        # проверка: только имена и даты
```

Почему токен, а не `supabase login` в CI: вход в CI интерактивный, а токен — единственный способ авторизовать CLI без браузера. Пароль БД не нужен (см. §4).

CI делает `db push --dry-run`, затем `db push --yes`, указывая проект через `--remote`, а не через `link`: так работа не зависит от того, связан ли каталог в конкретной машине или в кэше CI. Это проверено вручную на копии `supabase/` без `.temp/` и без `link`: с одним только `SUPABASE_ACCESS_TOKEN` команда `db push --dry-run --remote=wtpiyygnffemrboyjlwo` проходит. Seed на prod не применяется: тестовые данные в рабочей базе — это потерянные реальные данные. `config push` в CI тоже нет — по причине из §4.1.

**Отдельное ограничение при первом push.** GitHub не даёт заливать файлы `.github/workflows/*`, если у используемого git-токена нет области `workflow`. Признак: `refusing to allow an OAuth App to create or update workflow`. Лечится `gh auth refresh -s workflow` (откроется браузер) либо push через GitHub Desktop или веб-интерфейс. Токен-секрет `SUPABASE_ACCESS_TOKEN` здесь ни при чём — это право на изменение workflows в самом репозитории.

## 6. Правила безопасности

- **Никогда** `db reset --remote`: команда стирает удалённую базу.
- Схема prod меняется только миграцией, прошедшей local и `main`; руками в Studio — нет.
- Секретный ключ и строку подключения не коммитить, не логировать, не отдавать клиенту.
- Перед рискованной миграцией (удаление колонки, переименование) — проверить её на локальной копии с реальными по форме данными и сделать экспорт.
- Бесплатный облачный проект засыпает после недели неактивности: первый запрос после паузы дольше обычного.
