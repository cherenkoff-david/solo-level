# Solo Level — техническая архитектура

**Статус:** рабочий документ · версия 0.2  
**Связанные документы:** `solo-level-product-foundation.md`, `solo-level-progression-system.md`  
**Область:** стек, схема данных, безопасность, интеграция фронтенда и бэкенда первой версии.

---

## 1. Задача этого документа

Зафиксировать, из чего состоит приложение технически и какие решения приняты осознанно. Документ отвечает на вопросы: где живут данные, как считается прогрессия, как фронтенд говорит с бэкендом, как защищаются персональные данные, и какие решения приняты «пока так, на будущее пересмотрим».

Технические решения здесь подчинены продуктовым: персональные данные не должны утекать, прогресс не должен теряться или удваиваться, а доменная логика не должна быть заперта в коде интерфейса.

## 2. Общая картина

```text
Браузер (React SPA)
  │  HTTPS / JSON
  ▼
Бэкенд-платформа (аутентификация + REST/Auto-API + политики доступа)
  │
  ▼
PostgreSQL (реляционная БД)
  ├── users
  ├── spheres
  ├── goals / milestones
  ├── habits / tasks
  ├── completions
  └── reward_ledger   ← источник истины
```

Три уровня и одно правило:

| Уровень | Отвечает за | Не отвечает за |
| --- | --- | --- |
| **Клиент (React)** | Отображение, ввод, оптимистичный отклик | Расчёт истинного баланса XP, доверие к себе |
| **Бэкенд-платформа** | Аутентификация, доступ к данным, политики на уровне строк | Доменную бизнес-логику прогрессии, если её можно вынести в чистый модуль |
| **PostgreSQL** | Хранение, неизменяемая история, уникальные ключи, целостность | Внешний вид и подсказки |

**Правило:** истина о прогрессе — это журнал наград в базе. Любое число XP, уровня или ритма в интерфейсе — либо производное от журнала, либо кэш, помеченный как кэш.

## 3. Стек

| Слой | Выбор | Обоснование | Альтернатива, если понадобится |
| --- | --- | --- | --- |
| Клиент | React + Vite + TypeScript | Самый распространённый стек, проще искать помощь и документацию | SvelteKit — меньше кода, но меньше сообщества |
| Язык | TypeScript на клиенте и сервере | Один язык, общие типы домена между фронтом и бэком | — |
| Стили | Tailwind 4 (CSS-first, `@theme`) | Токены дизайна задаются как семантические переменные в одном месте, что нужно для тем; утилитарные классы не требуют выдумывать имена и плодить файлы. Детали — `design/direction.md` и `design/tokens.md` | CSS Modules или обычный CSS, если разметка станет читаемее без утилит |
| Бэкенд-платформа | Supabase (аутентификация + PostgreSQL + авто-API) | Не нужно писать сервер с нуля; реляционная БД в комплекте; бесплатный тариф достаточен (две среды — dev и prod) | Neon + собственный Node-бэкенд; «голый» Postgres |
| База данных | PostgreSQL | Реляционная модель идеально подходит журналу и связям; работает уровень строк | — |
| Аутентификация | Supabase Auth (email + пароль **и** ссылка на почту) | Встроена в платформу, не требует своего сервера сессий | Own JWT, если понадобится полный контроль |
| Локальная среда | Supabase CLI в Docker | Отдельный dev-слепок базы рядом с prod, проверка Auth и политик до выкладки | Облачный проект на бесплатном тарифе как «dev» |
| Хостинг клиента | Локальный сервер разработки теперь; статический хостинг позже | Разработка без внешних зависимостей, публикация по постоянному URL потом | — |

**Почему Supabase, а не «голый Postgres + Node».** Для одного разработчика-любителя ключевая экономия — не писать и не эксплуатировать сервер аутентификации, управление сессиями, миграции и слой доступа к данным. Supabase даёт это в комплекте с Postgres и политиками на уровне строк. Это осознанный компромисс: меньше кода — больше зависимости от платформы. Если зависимость станет проблемой, домен и схема данных переносятся в «голый» Postgres без переписывания логики, потому что домен от платформы не зависит (§5).

**Проверенные ограничения бесплатного тарифа** (на октябрь 2026, числа меняются — сверяться с прайс-страницей): 500 МБ базы, 50 000 активных пользователей в месяц, 2 активных проекта. Важное: **бесплатный проект засыпает после недели неактивности.** Для личного инструмента это означает, что после недельного перерыва первый вход может занять дольше (проект просыпается) — стоит проверить и, если раздражает, заложить в бюджет минимальный платный тариф.

## 4. Домен как отдельный модуль

Доменная логика (XP, кривые уровней, ритм, периоды, бонусы, вехи, отмена) живёт в отдельном TypeScript-пакете без зависимостей от React, от Supabase и от браузера.

```text
packages/
  domain/          ← чистый TypeScript, без побочных эффектов
    xp.ts          кривые XPNext(L, k), накопительный XP
    levels.ts      уровень по сумме XP, уровень сферы, ступени
    rhythm.ts      окна ритма, серия, бонус ритма
    periods.ts     periodKey из расписания и часового пояса
    reward.ts      расчёт награды, бонусы, надбавка за веху
    ledger.ts      правила неизменяемого журнала, ключи идемпотентности
    types.ts       типы сущностей, общие с клиентом и базой
  app/             ← React-клиент (Vite 8, React 19, TypeScript 7, Tailwind 4)
                     тонкий слой над доменом; дизайн-токены — в src/styles/index.css
    app/shell/     оболочка: AppShell (двухколоночная сетка, max-w 1200px),
                   Header (стеклянный sticky-хедер), navigation.ts
    app/spheres/   обзор сфер: spheres.ts (SPHERES + getSphereProgress,
                   PLACEHOLDER-данные до слоя журнала), SphereRadar.tsx (SVG-радар)
    app/screens/   экраны разделов (пока EmptyState)
```

Почему так:

- домен тестируется на встроенном `node:test` без Xcode, без браузера и без базы — проверено на этой машине;
- одну и ту же формулу нельзя написать по-разному на клиенте и на сервере (единственный источник — пакет);
- смена бэкенда или переход на другой клиент не трогает логику;
- числа из документов (кривая `1.05`, сферы `1.03`, окна ритма) становятся тестами, а не текстом, который расходится с кодом.

Первые тесты должны фиксировать именно те значения, что посчитаны в документах: `XPNext(1) = 100`, накопительный XP до уровня 20 ≈ 3 056, уровень сферы при делении внимания на три ≈ 60 дней до десятого.

## 5. Схема данных

Все таблицы, доступные клиенту, имеют `user_id` и политику доступа на уровне строк (§6).

### 5.1. Пользовательские сущности

| Таблица | Ключевые поля | Замечания |
| --- | --- | --- |
| `profiles` | `id` (= id пользователя аутентификации), `timezone`, `week_start`, `day_start_hour`, `level_curve_version`, `current_rule_version`, `created_at` | Настройки периода и версии правил из системы прогрессии |
| `spheres` | `id`, `user_id`, `name`, `color`, `archived_at`, `created_at` | 3–5 сфер; архивирование вместо удаления |
| `goals` | `id`, `user_id`, `title`, `type`, `indicator_*`, `status`, `created_at` | Не более одного активного числового индикатора |
| `milestones` | `id`, `user_id`, `goal_id`, `title`, `effort`, `completed_at` | Веха-контейнер (§6.3 системы прогрессии) |
| `habits` | `id`, `user_id`, `title`, `sphere_id`, `effort`, `schedule_*`, `milestone_id`, `archived_at` | Расписание: ежедневно / дни недели / N в неделю / N в месяц |
| `tasks` | `id`, `user_id`, `title`, `sphere_id`, `effort`, `goal_id`, `milestone_id`, `status`, `due_date` | Разовое действие, даёт XP один раз |
| `completions` | `id`, `user_id`, `source_type`, `source_id`, `period_key`, `occurred_at`, `note`, `volume` | Факт выполнения; **не** уникален по периоду: дополнительные отметки допустимы как статистика, XP не повторяется |
| `daily_checkins` | `id`, `user_id`, `local_date`, `state`, `note` | Необязательная дневная отметка самонаблюдения («полезно / нейтрально / мешает»); **не влияет на прогрессию**, нужна для оценки догфудинга |

**Про `completions` и уникальность.** Уникальность на период стоит **на журнале наград**, а не на фактах выполнения. Причина: система прогрессии, §5.4 разрешает несколько отметок одной привычки за период — они сохраняются как личная статистика, но не добавляют опыт. Если бы ограничение стояло на `completions`, лишние отметки было бы невозможно сохранить; если бы его не было на журнале, повторная отметка удваивала бы XP.

**Оговорка про `source_type` / `source_id`.** Ссылка на источник **полиморфная**: одна колонка указывает то на `habits`, то на `tasks`, то на `milestones` — в зависимости от `source_type`. Из-за этого поставить обычный внешний ключ на `source_id` нельзя: он указывал бы на разные таблицы. Целостность обеспечивается значением `source_type` и проверкой при записи. Если это когда-нибудь станет неудобно (например, понадобится каскадное удаление), схема разводится на отдельные ссылочные колонки или на таблицу-надстройку «действие». Для первой версии полиморфной ссылки достаточно, и она служит той же цели, что и в журнале наград.

### 5.2. Журнал наград — источник истины

```sql
-- append-only: только INSERT, никогда UPDATE/DELETE
reward_ledger (
  id             uuid primary key,
  user_id        uuid not null,
  occurred_at    timestamptz not null,
  source_type    text not null,      -- task | habit | milestone
  source_id      uuid not null,
  event_type     text not null,      -- base_xp | rhythm_bonus | first_step | milestone_bonus | reversal
  period_key     text not null,
  sphere_id      uuid,
  base_xp        integer not null default 0,
  bonus_xp       integer not null default 0,
  total_xp       integer not null,   -- может быть отрицательным только для reversal
  rule_version   text not null,
  reverses_id    uuid,               -- для компенсирующей записи
  idempotency_key text not null
)
```

**Три инварианта, которые обеспечивает база, а не приложение:**

1. **Одна награда на период — уникальный индекс по составному ключу.**
   `unique (user_id, source_type, source_id, period_key, event_type)`.
   Это правило, читаемое прямо в схеме: за один период у одной привычки или задачи не может быть двух базовых наград, двух бонусов ритма и так далее.
2. **Идемпотентность — детерминированный ключ.**
   `unique (user_id, idempotency_key)`, где ключ — детерминированная функция того же набора полей (как описано в системе прогрессии, §4). Вставка — `insert … on conflict do nothing`.
   *Замечание:* два уникальных индекса выше частично дублируют друг друга — оба запрещают повторную награду. Индекс по `idempotency_key` сохраняется отдельно, потому что именно он остаётся точкой идемпотентности, если правила периода когда-нибудь изменятся; но при первом проектировании достаточно одного, и **рекомендуется оставить составной индекс `(user_id, source_type, source_id, period_key, event_type)`** как единственный, а `idempotency_key` сделать производной колонкой без собственного индекса — иначе схема утверждает одно правило дважды и однажды они разойдутся.
   Почему проверка в приложении не годится: «посмотреть, не начислено ли уже» перед вставкой проигрывает гонку при двух одновременных запросах; уникальный индекс — нет.
3. **Неизменяемость.** Запрет `UPDATE` и `DELETE` на `reward_ledger` через триггер, который поднимает исключение. Отмена выполнения — это новая строка с отрицательным `total_xp` и заполненным `reverses_id`, а не правка старой.

**Производительность.** Индексы по `(user_id, occurred_at desc)`, `(user_id, sphere_id)`, `(user_id, source_type, source_id)`. Политика доступа фильтрует по `user_id`, поэтому индекс по ведущему `user_id` обязателен — иначе политика сама становится причиной медленных запросов.

### 5.3. Что НЕ хранится как отдельный источник истины

| Значение | Почему не хранится отдельно |
| --- | --- |
| Общий XP и общий уровень | Считаются суммой журнала; хранить — значит иметь два расходящихся числа |
| Уровень сферы | Производное от суммы журнала по сфере (система прогрессии, §8.3) |
| Показатель ритма | Вычисляется из истории выполнений по расписанию |
| Серия | Вычисляется; не влияет на награду, поэтому и хранить нечего |

Кэш допустим только как оптимизация с явным признаком кэша и возможностью пересчитать из журнала. Для одного пользователя и десятков записей в день оптимизация не нужна вовсе.

## 6. Безопасность

### 6.1. Модель доступа

Каждая таблица с пользовательскими данными получает `user_id` и политику на уровне строк. Канонический шаблон для PostgreSQL / Supabase:

```sql
alter table habits enable row level security;

create policy "habits_select_own" on habits
  for select to authenticated
  using ((select auth.uid()) = user_id);

create policy "habits_write_own" on habits
  for all to authenticated
  using ((select auth.uid()) = user_id)
  with check ((select auth.uid()) = user_id);
```

Четыре вещи, которые здесь неочевидны и о которых известно из документации (см. §13 источников):

- **RLS не включается автоматически на новых таблицах.** Её нужно включать явно для каждой таблицы; таблица без RLS при наличии прав доступа читается кем угодно. Это ошибка номер один в подобных проектах.
- **Права и политики — разные вещи.** Новая таблица может получить широкие права для ролей доступа, и «добавление политики прав не отменяет». Права нужно выдавать явно и узко.
- **Вызовы в политике оборачиваются в `select`** — `(select auth.uid())`, а не `auth.uid()` — чтобы значение вычислялось один раз на запрос, а не на каждую строку.
- **`service_role` / секретный ключ имеет обход RLS.** Он никогда не попадает в браузер. Он существует только для серверных административных задач, которых в первой версии нет вообще.

### 6.2. Ключи и секреты

| Ключ | Где живёт | Почему |
| --- | --- | --- |
| Публикуемый (publishable / legacy anon) | В клиенте, в переменной окружения сборки | Не секрет: он даёт ровно то, что разрешают политики RLS |
| Секретный (secret / legacy service_role) | Только в серверном окружении, никогда в браузере и никогда в репозитории | Полный доступ мимо политик |
| Строка подключения к базе | Только в серверном окружении и локальном `.env` | Прямой доступ к базе, мимо политик |

Правила гигиены: `.env` в `.gitignore` (уже настроено), в репозиторий попадает только `.env.example` с именами переменных без значений; ключи не логируются; при подозрении на утечку секретный ключ немедленно ротируется.

### 6.3. Прочая защита

- **Транспорт** — только HTTPS. При локальной разработке трафик не покидает машину.
- **Аутентификация** — вход по email и паролю, подтверждение почты. Долгоживущие токены: короткоживущий токен доступа и одноразовый токен обновления; повторное использование старого токена обновления отзывает сессию. Это поведение платформы, и его не нужно реализовывать самому.
- **Валидация на сервере.** Клиент может присылать что угодно: уровень усилия, объём, дату. Проверка диапазонов и допустимых значений происходит на сервере или в БД ограничениями; клиентская валидация — только для удобства ввода.
- **Никаких доверенных полей с клиента.** Награда, `rule_version`, `total_xp` и ключ идемпотентности формируются на стороне, которую контролирует приложение, а не приходят готовыми из браузера.
- **Свой ID пользователя нельзя указать вручную.** `user_id` берётся из аутентификации, а не из тела запроса; иначе политика станет декоративной.
- **Ограничение частоты** на чувствительные операции (создание записей наград) — на будущее; пока роль барьера играет уникальный индекс идемпотентности.

### 6.4. Персональные данные

Приложение хранит: адрес почты, часовой пояс, историю действий и заметки. Данные не продаются и не передаются третьим лицам — это следует из продуктовых принципов. Экспорт по запросу пользователя поддерживается (выгрузка файлом). Удаление учётной записи должно удалять пользовательские данные каскадно; в первой версии достаточно предусмотреть это на уровне схемы (внешние ключи с `on delete cascade`), а сценарий удаления добавить позже.

## 7. Интеграция клиента и бэкенда

### 7.1. Как клиент говорит с данными

Клиент использует официальный клиент платформы. Чтение — простые выборки с фильтром по `user_id` (политика подставит его и без фильтра, но явный фильтр делает запрос быстрым и читаемым). Запись сложных операций — не прямая вставка из браузера, а вызов функции на стороне базы.

```ts
// чтение: сегодняшние привычки и задачи
const { data } = await supabase
  .from('habits')
  .select('*')
  .eq('user_id', userId)
  .is('archived_at', null);

// запись: подтверждение выполнения + начисление награды
const { data } = await supabase.rpc('complete_action', {
  p_source_type: 'habit',
  p_source_id: habitId,
  p_occurred_at: new Date().toISOString(),
});
```

### 7.2. Почему подтверждение выполнения — функция базы, а не вставка из клиента

Подтверждение — это транзакция из нескольких шагов, описанных в системе прогрессии, §12: проверить расписание, вычислить ключ идемпотентности, создать выполнение, посчитать награду, записать в журнал. Если делать это несколькими запросами из браузера, то сбой на середине оставит неполное состояние, а два быстрых нажатия создадут две награды.

Решение: одна функция `complete_action(...)`, выполняемая в одной транзакции. Формулы награды передаются не с клиента, а берутся из `rule_version`, действующей для пользователя.

**Решено: расчёт живёт в доменном модуле, SQL-функция только оркестрирует.** Серверная функция `complete_action` не переписывает формулы на SQL. Она валидирует запрос, вызывает доменный модуль для расчёта награды по действующей `rule_version`, и записывает готовые строки в журнал в той же транзакции. В SQL остаются только инварианты целостности (уникальность, запрет правки, внешние ключи) — то, что дешевле и надёжнее проверить средствами базы.

Почему так: формулы кривых XP и уровней сфер уже покрыты тестами в доменном пакете на встроенном `node:test`. Если продублировать их в SQL, тесты перестанут быть доказательством — они будут проверять одну реализацию, пока в работе другая. Дублирование на двух языках рано или поздно даёт расхождение, а расхождение в начислении опыта означает недоверенные числа в журнале.

Что это означает технически: доменный модуль должен быть исполняемым в серверном окружении. Если база — управляемая платформа, а функция исполняется средствами базы, домен выносится в **серверную функцию-обёртку** (например, edge function), которая считает награду доменом и пишет в базу через транзакцию. Это чуть больше инфраструктуры, чем чистый SQL, но сохраняет единственный источник формул. Альтернатива — держать домен только на сервере и не давать клиенту никаких формул вообще, что и так требуется (§7.3).

### 7.3. Клиент не доверяет себе

Три правила для фронтенда:

- **Оптимистичный отклик разрешён, но необязателен.** Можно показать «+35 XP» сразу, но итог берётся из ответа функции; если ответ расходится — интерфейс показывает серверное значение.
- **Кэш помечается.** Локально закэшированный прогресс — удобство, а не истина; при расхождении побеждает журнал.
- **Ошибки идемпотентности — норма.** Повторное подтверждение должно возвращать тот же результат, а не ошибку; интерфейс ведёт себя так, будто награда уже есть.

### 7.4. Вход: пароль и ссылка одновременно

Поддерживаются оба способа: вход по email и паролю и вход по одноразовой ссылке на почту. Оба — штатные методы платформы, и оба используют один и тот же профиль пользователя; пользователь не заводит две учётные записи. Ссылка на почту удобна как основной способ, пароль — как запасной, если почта подводит или нужно войти на новом устройстве.

Следствие для экрана входа: одна форма с полем почты, кнопка «войти по ссылке» и раскрывающийся блок с паролем, а не два отдельных экрана. Это же поведение нужно проверять локально, поэтому локальный перехватчик писем (§8.2) обязателен на этапе разработки.

## 8. Локальная разработка, среды и хостинг

### 8.1. Две среды

Есть два слепка базы данных и два набора настроек:

| Среда | Что это | Где живёт | Данные |
| --- | --- | --- | --- |
| **dev** | Локальный стек для разработки | Локальная машина, поднимается через Supabase CLI в Docker | Синтетические, можно вайпать |
| **prod** | Рабочее приложение | Облачный проект платформы, постоянный URL клиента | Реальные, бэкапятся |

**Бесплатный тариф позволяет два активных проекта** (проверено, §13), поэтому схема «один проект dev + один проект prod» укладывается в бесплатный план. Важная оговорка из документации: проект, схема которого уже совпадает с prod, **нельзя переиспользовать как dev** — это отдельный проект, а не копия рабочего.

Рекомендуемая последовательность изменений схемы: локально → dev-проект → prod-проект, никогда не наоборот. Прямое применение миграций на prod без прогонки на dev — самая частая причина потери данных своими руками. В будущем это автоматизируется: `develop` деплоится на dev-проект, `main` — на prod, каждый со своими секретами.

### 8.2. Локальный запуск

```text
Локально:   npx supabase init    →  создаёт supabase/ (config.toml, migrations/, seed.sql)
            npx supabase start   →  Postgres + Auth + Studio + Mailpit в Docker
            npx supabase db reset→  миграции с нуля + seed
            npm run dev          →  React-клиент смотрит на локальный стек
Позже:      supabase link        →  связать с облачным проектом
            supabase db push     →  применить миграции (сначала dev, потом prod)
            сборка клиента       →  хостинг с постоянным URL, смотрит на prod
```

**Требуется запущенный Docker.** Полный локальный стек работает только в Docker-совместимой среде (Docker Desktop; на macOS документация рекомендует OrbStack). На машине Docker установлен (проверено), но демон при проверке не был запущен — его нужно включить перед `supabase start`.

**Локальные порты по умолчанию** (из документации): gateway/API `54321`, Postgres `54322`, Studio `54323`, перехватчик почты `54324`. Детали и порты задаются в `config.toml`, который создаётся при инициализации и **хранится в репозитории**.

**Локальная почта.** Перехватчик писем — **Mailpit** (преемник старого Inbucket), по умолчанию на `http://127.0.0.1:54324`. Все письма локальной аутентификации (ссылка на вход, подтверждение адреса) попадают туда и не покидают машину; лимита писем локально нет. Важная деталь: **локально подтверждение почты по умолчанию выключено**, а на облачном проекте — включено. Чтобы тестировать сценарий подтверждения локально, его включают в `config.toml`.

**Что важно знать про локальные данные:** `db reset` удаляет локальную базу и пересобирает её из миграций и seed — локальные записи теряются. Это нормально для dev. `supabase stop` данные сохраняет.

**Порт — один на машину.** Порты в `config.toml` фиксированные, поэтому второй `supabase start` на той же машине упадёт с «port already allocated». Для одного проекта это не проблема; при втором рабочем каталоге потребуется `supabase stop` или отдельная конфигурация портов.

### 8.3. Миграции как единственный способ менять схему

Схема (таблицы, индексы, политики, функции, триггеры) меняется **только миграциями** — SQL-файлами в `supabase/migrations/`, хранящимися в репозитории, — и никогда вручную через визуальный редактор. Причина: ручное изменение не попадёт в историю, следующий `db reset` его потеряет, и prod разойдётся с dev.

Цикл работы: `supabase migration new <имя>` создаёт файл миграции; `db reset` применяет всё локально с нуля; `db diff` умеет сгенерировать миграцию по изменениям, сделанным в Studio. RLS-политики, уникальные индексы идемпотентности и триггер запрета правки журнала — обычные SQL-миграции наравне с созданием таблиц.

**Порядок продвижения: локально → dev-проект → prod-проект, никогда наоборот.** Для облачных проектов миграции применяются командой `db push`; перед этим полезна проверка `--dry-run`, а от `--include-seed` на prod следует держаться в стороне: seed-данные не место в рабочей базе. Отдельная опасность — `db reset --remote`: он стирает данные удалённой базы и годится только для dev.

### 8.4. Секреты и переменные окружения

Клиент (Vite) читает конфигурацию из переменных с префиксом `VITE_`: адрес проекта и **публикуемый** ключ. Vite отдаёт в код только переменные с этим префиксом, поэтому секретный ключ туда случайно не попадёт — но полагаться только на префикс не стоит, это правило, а не защита. Публикуемый ключ в клиенте безопасен, потому что он даёт ровно то, что разрешают политики доступа. **Секретный ключ и строка подключения к базе в клиент не попадают никогда** — только в серверное окружение и локальный `.env` (в `.gitignore`). В репозиторий попадает `.env.example` с именами переменных без значений, отдельно для dev и prod; для CLI-переменных в `config.toml` используется подстановка `env(...)` из корневого `.env`.

## 9. Тестирование и проверка

| Уровень | Инструмент | Что проверяет |
| --- | --- | --- |
| Домен | `node:test` (встроенный, без зависимостей) | Кривые XP, уровни и уровни сфер, ритм, периоды, бонусы, надбавка за веху, отмена |
| Схема | миграции + проверочные запросы | Уникальные индексы идемпотентности, запрет `UPDATE`/`DELETE`, каскады |
| Доступ | отдельный тест-пользователь | Пользователь A не видит данные пользователя B ни при каких запросах |
| Локальная среда | `supabase db reset` | Миграции применяются с нуля, seed загружается, схема воспроизводима |
| Вход | Mailpit (локально) | Ссылка на почту и подтверждение адреса работают без внешней почты |
| Интеграция | сквозной сценарий | Подтверждение → журнал → пересчёт XP и уровня |
| Клиент | по мере роста | Ключевые сценарии вручную; автотесты интерфейса — позже |

Проверка изоляции данных между пользователями — обязательна и должна быть первой: она ловит ошибку, которую иначе обнаружит посторонний человек на ваших данных.

## 10. Открытые технические вопросы

1. **Импорт данных из файла** — нужен ли он в первой версии, или достаточно выгрузки. Рекомендация: экспорт в первой версии, импорт — по необходимости.
2. **Часовой пояс и начало дня** — где хранится источник (в профиле) и как обрабатывается смена пояса. Уже решено в системе прогрессии, §5.5; здесь нужно только подтвердить поля хранения.
3. **Форма примера привычки в онбординге** — какое действие предлагается как первое и с каким усилием (§13.1 п. 6 продуктовой основы). Влияет на стартовый seed и на текст онбординга.
4. **Аналитика догфудинга** — как фиксируется ежедневная отметка «полезно / нейтрально / мешает»: отдельной кнопкой в конце дня, заметкой к последнему действию или отдельной сущностью. Решается в пользовательских сценариях.

### 10.1. Решённые вопросы

| Вопрос | Решение | Где обосновано |
| --- | --- | --- |
| Где живёт расчёт награды | Доменный модуль; SQL только инварианты | §7.2 |
| Среда разработки | Локальный стек Supabase CLI + отдельный prod-проект | §8.1, §8.2 |
| Способ входа | Email и пароль **и** ссылка на почту (оба) | §6.3, §8.2 |
| Секреты | Публикуемый ключ в клиенте, секретный — никогда | §6.2 |
| Сферы | Вклад в общий XP + собственный уровень (кривая `1.03`) | система прогрессии, §8.3 |

## 11. Решения, которые следуют из этой архитектуры

1. Домен пишется и тестируется **до** интерфейса и до подключения базы: формулы — самая дорогая часть ошибки.
2. Схема базы проектируется вокруг журнала, а не вокруг «текущих значений».
3. Ошибка изоляции данных между пользователями — самая серьёзная из возможных, поэтому тест на неё пишется рано.
4. Секретный ключ никогда не попадает в браузер; это проверяется один раз на этапе настройки и больше не обсуждается.
5. Всё, что можно посчитать, не хранится. Хранится только то, что нельзя восстановить: сама история.
6. Коммиты делает автор вручную; агент работает локально.

## 12. Порядок реализации

```text
1. Доменный пакет + тесты на числа из документов
2. Локальная среда: Supabase CLI, миграции, seed
3. Схема БД: таблицы, индексы, RLS-политики, запрет правки журнала
4. Подтверждение выполнения: доменный расчёт + запись в журнал одной транзакцией
5. Минимальный клиент: вход → «Сегодня» → отметка → карточка награды
6. Проверка изоляции между пользователями
7. Догфудинг 8+ недель
8. Выкладка на prod-проект и постоянный URL
9. Расширение: цели и вехи, обзор недели, уровни сфер, ступени
```

Каждый шаг заканчивается проверяемым результатом: 1 — зелёные тесты домена; 2 — локальный стек поднимается, вход и ссылка на почту работают; 3 — миграции применяются, уникальные индексы и триггер отвергают неверные записи; 4 — повторный вызов подтверждения не удваивает награду; 5 — цикл проходится вручную от входа до карточки; 6 — тест-пользователь не читает чужие данные.
