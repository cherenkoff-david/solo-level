# Solo Level

Личный трекер привычек и задач с игровой прогрессией: реальные действия превращаются в опыт, уровни и видимый прогресс по направлениям жизни.

**Статус:** в разработке. Готовы доменный пакет (`@solo/domain`) и каркас клиента (`@solo/app`); содержимое экранов и серверная часть — впереди.
**Режим:** личный инструмент одного пользователя (автора проекта), не публичный продукт.

---

## 1. Что это

Приложение, которое превращает ежедневные небольшие действия в измеримый прогресс: опыт, уровни, ступени, вклад в сферы жизни. Идея вдохновлена мотивационной петлёй «системы» из progression fantasy, но без копирования конкретной франшизы и без чужих терминов.

Главный принцип: **помочь действовать вне экрана**, а не удержать пользователя в интерфейсе. Поэтому в продукте нет штрафов за пропуски, потери опыта, давления на ежедневный вход и платных ускорителей.

## 3. Стек и почему именно он

Краткое обоснование; подробное — в `docs/solo/technical-architecture.md`, §3.

### Фронтенд: React + Vite + TypeScript

**Почему:** самый распространённый стек — проще искать ответы и примеры, что для одного разработчика важнее «элегантности». Vite даёт быстрый старт и сборку без настройки. TypeScript обязателен, потому что домен (XP, уровни, журнал) — это много числовых правил, а типы ловят ошибки вроде «усилие передали строкой» ещё до запуска.

**Альтернативы, которые рассматривались:**

| Альтернатива | Плюсы | Почему не выбрана |
| --- | --- | --- |
| Svelte / SvelteKit | Меньше кода, часто приятнее | Меньше сообщества и примеров; помощь искать дольше |
| Vue | Простой вход, хорошая документация | React чуть более распространён в вакансиях/примерах; разница невелика |
| Без фреймворка (ванильный JS) | Минимум зависимостей | Ручная работа с состоянием быстро становится громоздкой |
| Next.js | SSR, маршрутизация из коробки | Избыточно: приложению не нужен серверный рендеринг, а сложность выше |

### Бэкенд и база: Supabase (PostgreSQL + Auth)

**Почему:** для одного разработчика-любителя главная экономия — не писать и не эксплуатировать сервер аутентификации, управление сессиями, миграции и слой доступа. Supabase даёт это в комплекте с реляционным PostgreSQL и **политиками доступа на уровне строк (RLS)**. Это осознанный компромисс: меньше кода — больше зависимости от платформы. Домен при этом от платформы не зависит, поэтому миграция на «голый» Postgres возможна без переписывания логики.

**Почему реляционная БД, а не документная:** прогресс — это история операций (журнал наград) и связи между сущностями (привычка → сфера → цель). Нужны транзакции, уникальные ограничения и целостность — сильные стороны SQL. Уникальный индекс «одна награда за период» надёжно защищает от двойного начисления, чего в документной модели добиться сложнее.

**Альтернативы, которые рассматривались:**

| Альтернатива | Плюсы | Почему не выбрана |
| --- | --- | --- |
| Firebase | Простой старт, реальное время | Документная модель, свои правила доступа; хуже ложится на реляционные правила прогрессии |
| Neon + свой Node-бэкенд | Полный контроль, «чистый» Postgres | Нужно самому строить аутентификацию, сессии, слой доступа — много работы |
| «Голый» Postgres + Node | Максимальный контроль, без вендор-лока | То же самое плюс эксплуатация БД на своей стороне |
| Turso / libSQL | SQLite на краю, прост | Не Postgres; нет RLS-модели; другая модель доступа |
| MongoDB | Гибкая схема | Прогресс требует транзакций и ограничений целостности; гибкость здесь во вред |

### Локальная среда: Supabase CLI в Docker

**Почему:** нужны два слепка базы — dev и prod. Локальный стек через CLI даёт изолированную песочницу, где можно вайпать данные и проверять миграции и политики до выкладки. Бесплатный тариф Supabase включает два облачных проекта, поэтому схема «локально → dev-проект → prod-проект» укладывается без затрат.

### Домен как отдельный модуль

**Почему:** формулы XP, уровней и ритма — самая дорогая часть ошибки и единственная, которую нельзя исправить вёрсткой. Домен — чистый TypeScript без зависимости от React, Supabase и браузера, поэтому его можно покрыть тестами на встроенном `node:test` **до** появления интерфейса и базы. Плюс одна формула живёт в одном месте, а не дублируется на клиенте и в SQL.

## 4. Команды

Пошаговая инструкция для тех, кто просто хочет посмотреть приложение: `docs/local-run.md`.

```bash
# Тесты доменов прогрессии и финансов (встроенный node:test)
npm test

# Генерация чисел прогрессии — единственный источник чисел для документов
# (правило происхождения чисел, см. AGENTS.md)
npm run gen:progression

# Локальная среда (когда появится схема БД; нужен запущенный Docker)
npx supabase start         # поднять локальный стек
npx supabase db reset      # применить миграции с нуля + seed
npm run dev                # клиент разработки

# Выкладка (позже)
npx supabase db push       # применить миграции в облачный проект
npm run build              # сборка клиента
```

**Правило происхождения чисел.** Любое число прогрессии в `docs/` (накопительный XP, дни до уровня, темп сферы) должно быть получено `npm run gen:progression`, а не набрано руками. Если число нельзя воспроизвести скриптом — это ошибка документа.

```text
docs/                      проектная документация (актуальный источник решений)
  README.md                карта документации: два направления
  solo/                    направление «прогрессия»: обзор, продукт, система прогрессии,
                           архитектура, сценарии
  finance/                 направление «деньги»: требования, модель данных, архитектура

  direction.md             как выглядит интерфейс и почему именно так
  tokens.md                значения: палитра, типографика, размеры, радиусы
  references/              референсы со скриншотом и разбором «что берём / что нет»
  screenshots/             скриншоты для проверки (снимаются npm run shot)
packages/
  domain/                  чистая логика: XP, уровни, ритм, периоды, награда, журнал
    src/                   исходники (без зависимостей от UI и БД)
    test/                  тесты на node:test
  app/                     React-клиент (Vite + React + TypeScript + Tailwind)
    src/app/shell/         оболочка: AppShell, Header, navigation
    src/app/landing/       входная страница /welcome: hero-демо, «Искра», этапы,
                           сферы, финансы, FAQ, CTA
    src/app/screens/       SoloPlaceholder — общий экран «раздел в разработке»
    src/app/spheres/       обзор сфер и SVG-радар (не монтируется, пока идёт заглушка)
    src/app/finance/       раздел «Финансы»: обзор, календарь, операции, настройки, обучение
    src/styles/index.css   дизайн-токены (@theme) и анимации
    src/styles/landing.css масштаб и движение входной страницы
    tests/                 Playwright: скриншоты и проверки
  finance/                 домен финансов: деньги, серии, план, снимки, баланс
scripts/
  gen-progression.ts       печатает ориентиры прогрессии для документов
supabase/                  (план) конфигурация, миграции, seed
```

## 6. Текущее состояние

Реализовано: доменные пакеты `@solo/domain` (XP и уровни, периоды и часовые пояса, ритм и бонусы, расчёт награды, неизменяемый журнал) и `@solo/finance` (деньги, серии, план, снимки месяцев, баланс) — 100 тестов на встроенном `node:test`. Клиент `@solo/app`: оболочка с верхним стеклянным хедером (Сегодня / Прогресс / Сферы / Настройки / Финансы), дизайн-токены, скриншоты через Playwright. Разделы Solo пока показывают один общий анимированный экран-заглушку «раздел в разработке»; входная страница `/welcome` показывает работающий продукт (hero-демо, этапы, сферы, финансы). Раздел «Финансы» работает на локальном состоянии браузера и включает обучающий онбординг.

Не начато: схема БД, серверная логика, содержимое разделов Solo, локальная среда Supabase.

## 7. Правила работы над проектом

- Подробные правила для агента — в `AGENTS.md`.
- Коммиты делает автор вручную. Агент работает локально и не выполняет `git commit` / `git push` без явной просьбы.
- Секреты (ключи, строки подключения) не попадают в репозиторий: `.env` в `.gitignore`, в репозитории только `.env.example`.
- Документ — источник истины о решениях. Изменение правила в коде без обновления документа считается незавершённой работой.
