# Правила работы агента (AGENTS.md)

Этот файл описывает, как агент Kilo должен вести работу в проекте **Solo**.
Правила обязательны к соблюдению по умолчанию. Дополняется по ходу настройки.

---

## 1. Язык и стиль общения

- Отвечай на русском языке, если пользователь пишет по-русски.
- Будь кратким, прямым и по делу: без вступлений, извинений и «воды».
- Не заканчивай ответ вопросом ради продолжения диалога — формулируй результат как финальный,
  если не требуется настоящее решение пользователя.
- Для реальных развилок используй инструмент вопроса, а не догадки.

## 2. Скрипты и автоматизация

- **Сначала используй уже установленные в проекте скрипты и инструменты**, а не изобретай новые.
  Перед запуском команд проверяй `package.json` (scripts), `Makefile`, конфиги CI, `AGENTS.md`.
- Предпочитай существующие команды: тесты, линтеры, форматтеры, сборка.
- Не добавляй новые зависимости без явной необходимости и без согласования.
- Если не знаешь правильную команду — спроси пользователя и предложи записать её в этот файл,
  чтобы использовать в будущем.
- После завершения задачи запускай линт/типчек/тесты, если они доступны в проекте.

## 3. Контекст и память

- **Помни контекст сессии**: не переспрашивай то, что уже сказано или сделано.
- Храни проектные знания в репозитории (документация в `docs/`, этот `AGENTS.md`),
  а не только «в голове» сессии.
- Перед изменениями учитывай, что уже есть в коде и документации; не дублируй и не противоречь.
- Существенные договорённости и решения фиксируй в документации проекта.
- При возвращении к работе сначала сверяйся с текущим состоянием репозитория (`git status`, структура).

## 4. Изучение проекта

- **Изучай проект по необходимости**: перед правками смотри соседние файлы, импорты,
  соглашения об именовании, используемые библиотеки и фреймворки.
- Не предполагай наличие библиотеки — проверяй, что она реально используется в проекте.
- Соблюдай Code Style проекта; **не добавляй комментарии в код, если не попросили**.
- Используй поиск по коду и чтение файлов вместо догадок.
- Проверяй структуру каталогов, чтобы понять назначение кода по расположению файлов.

## 5. Субагенты и параллельная работа

- **Подключай субагентов для ускорения работы**, когда задача разбивается на независимые части.
- Независимые операции выполняй параллельно: несколько чтений/поисков за один шаг.
- Делегируй субагентам исследование и рутинные многошаговые задачи, чтобы экономить контекст.
- После делегирования не дублируй работу субагента сам.
- Для создания видимых сессий Agent Manager — только по явной просьбе пользователя.

## 6. Git и изменения

- **Не заливай изменения в git без явного указания пользователя.**
  Запрещено без команды: `git commit`, `git push`, создание PR, amend, force-push.
- Коммить только те файлы, которые нужны; не коммить секреты и `.env`.
- Соблюдай существующий стиль сообщений коммитов (Conventional Commits в этом проекте).
- Перед возможным коммитом показывай `git status` / `git diff`; стейджи только нужное.

## 7. Безопасность и аккуратность

- Никогда не логируй и не коммить секреты, ключи и токены.
- Не выполняй разрушительные операции (удаление данных, `reset --hard`, `clean`) без подтверждения.
- Не создавай лишние файлы без необходимости; предпочитай правку существующих.
- Не создавай документацию (`*.md`) проактивно, если не попросили.

## 8. Обучающий режим ответов

Пользователь — системный аналитик и учится на этом проекте: цель не только получить работающее приложение, но и понимать, **как** оно устроено, **почему** приняты те или иные решения и какова специфика используемых технологий.

Требования к ответам:

- **Объясняй «почему», а не только «что».** Когда предлагается решение, называй причину, альтернативы и то, почему они отклонены.
- **Вводи термины и специфику.** При первом использовании сложного понятия (например, RLS, идемпотентность, append-only журнал, транзакция, миграция) давай краткое пояснение по существу — что это и зачем, а не отсылку к документации.
- **Показывай связь с практикой аналитика.** Где уместно, проводи параллели с привычными артефактами системного анализа: требования, ERD, диаграммы последовательности, спецификации, границы систем, интеграции. Модель данных, сценарии и границы ответственности компонентов — это тот же материал, что и на работе.
- **Фиксируй решения и их обоснование в документации `docs/`**, а не только в переписке: это и есть «память проекта».
- **Не превращай ответ в лекцию.** Объяснение должно быть достаточным и по делу: короткое пояснение + ссылка на документ, где детали, - лучше длинного отступления.

## 9. Специфика проекта Solo

- **Что это:** личный трекер привычек с игровой прогрессией; личный инструмент одного пользователя, не публичный продукт.
- **Платформа:** веб-приложение (React + Vite + TypeScript), сервер и БД — Supabase (PostgreSQL + Auth + RLS).
- **Ключевой принцип:** истина о прогрессе — неизменяемый журнал наград в базе; всё вычисляемое (XP, уровни, ритм) считается, а не хранится счётчиком.
- **Домен:** отдельный модуль чистого TypeScript без зависимостей от UI и БД, тесты на встроенном `node:test`.
- **Виды прогресса:** общий XP, общий уровень (кривая `1.05`), уровень сферы (кривая `1.03`), ритм привычки, ступени, вехи.
- **Среды:** локальный стек Supabase CLI (dev) и облачный проект (prod). Порядок продвижения: локально → dev → prod, никогда наоборот.
- **Нельзя:** штрафы и потеря XP за пропуск, ежедневный бонус за вход, платные ускорители, случайные награды, защищённые названия и термины франшизы «Solo Leveling» (см. `docs/solo-level-product-foundation.md`, §6).
- **Документация — источник истины:** `docs/solo-level-overview.md`, `solo-level-product-foundation.md`, `solo-level-progression-system.md`, `solo-level-technical-architecture.md`, `solo-level-user-flows.md`. При расхождении кода и документа — исправляется то, что ошибочно, но молча не расходиться.
- **Проверка чисел:** любые числа прогрессии (кривые, накопительный XP, темп) перед публикацией пересчитываются в коде, а не берутся на веру из текста.
- **Правило происхождения чисел:** любое число прогрессии, попадающее в документ (накопительный XP, дни до уровня, темп сферы), должно быть **получено запуском кода**, а не набрано руками. Реализация — скрипт `npm run gen:progression` в корне репозитория; он печатает ориентиры, которые затем переносятся в `docs/`. Если число в документе нельзя воспроизвести этим скриптом — это ошибка документа, а не кода. Причина правила: расхождение текста и расчёта уже возникало дважды (коэффициент `1.12` и таблица рангов), и оба раза его находили вручную.

### Установленные скиллы и их применимость к стеку

В глобальном каталоге `~/.kilo/skills/` установлены четыре авто-вызываемых (model-invoked) скилла. Стек Solo — **React + Vite + TypeScript + Supabase**, без Next.js, поэтому при их срабатывании нужно отделять универсальное от платформенной специфики:

- **`find-skills`** — стек-нейтрален, применим без оговорок.
- **`web-design-guidelines`** — общие правила Web Interface Guidelines (доступность, взаимодействие, типографика); применяются к любой вёрстке, специфики Next.js не несёт.
- **`vercel-react-best-practices`** — из 70 правил берять только релевантные Vite/SPA: ререндеры, мемоизация, работа с DOM/JS-уровнем, обработчики событий. Правила категорий Next.js/серверных компонентов (`server-*`, RSC, маршруты App Router, серверные экшены) в Solo **неприменимы** — не переносить их в код.
- **`design-taste-frontend`** — ориентирован на лендинги/публичные страницы и Next.js; в Solo целевой UI — рабочие экраны трекера (дашборд, привычки, прогресс), а не маркетинговый сайт. Использовать его принципы «осознанных решений вместо AI-дефолтов» можно, но не тащить дословно лендинговые шаблоны и не выдумывать публичные страницы, которых в продукте нет.

Общее правило: при конфликте между рекомендацией скилла и спецификой Solo (стек, продуктовые ограничения из §6 `docs/solo-level-product-foundation.md`, единственный пользователь) — приоритет у специфики проекта.
