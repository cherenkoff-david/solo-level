# Как строить свою дизайн-систему

Практическая инструкция: где искать дизайн-системы и референсы, как из чужой системы сделать свою,
как работать с ней дальше и как в этом участвует агент.

Документ — продолжение `design/design-systems.md`: там выбор базы и лицензии, здесь — процесс.

---

## 1. Короткий ответ

Да, подход рабочего: **взять систему как каркас и вырастить на нём свою**. Но с уточнением, без
которого он превращается в копирование.

Дизайн-система — это не внешность. Внешность — следствие. Система состоит из пяти слоёв, и
заимствовать нужно нижние, а не верхний:

| Слой | Что это | Откуда берём | Что делаем сами |
| --- | --- | --- | --- |
| 1. Принципы | 5–7 проверяемых правил: что важнее при конфликте | Ниоткуда — выводим из продукта | Полностью свои |
| 2. Токены | Цвет, типографика, отступы, радиусы, движение | Механика — у систем; значения — у продукта | Свои значения |
| 3. Примитивы | Поведение и доступность: диалог, меню, слайдер | Radix / Base UI / React Aria | Стилизация своя |
| 4. Компоненты | Примитив, одетый в токены: кнопка, поле, карточка | shadcn как заготовка кода | Своя анатомия и состояния |
| 5. Паттерны экранов | Как компоненты собираются в «Сегодня», «Финансы» | Идеи — из референсов | Полностью свои |

Уникальность появляется не на слое 4 (кнопку все рисуют похоже), а на слоях 1, 2 и 5: в правилах,
значениях и в том, как экран отвечает на реальные сценарии продукта. Кнопка-«как у Linear» никого не
делает уникальным; уникальной делает связка «пропуск не отнимает XP → журнал неизменяем → интерфейс
не показывает штрафов и не давит».

Что законно, а что нет — в `design-systems.md` §6. Кратко: идеи, композиция, приёмы и механика
токенов не охраняются; чужие исходники, ассеты, шрифтовые файлы, логотипы и названия — охраняются.

## 2. Где искать

Источники делятся на четыре типа, и путать их нельзя: из каждого берут разное.

### 2.1. Стандарты поведения (обязательный минимум)

| Источник | Что берём |
| --- | --- |
| WCAG 2.2 (`w3.org/TR/WCAG22/`) | Нормы контраста, фокуса, размеров цели, работы с клавиатуры |
| WAI-ARIA Authoring Practices (`w3.org/WAI/ARIA/apg/`) | Как ведёт себя диалог, меню, табы, комбобокс: клавиши, роли, фокус |
| Web Interface Guidelines | Бытовые правила: `:focus-visible`, `prefers-reduced-motion`, `autocomplete`, семантика форм |

Эти документы не «вдохновляют» — они задают критерий приёмки. Компонент, который их нарушает,
не принимается, каким бы красивым он ни был.

### 2.2. Каталоги и документация систем (механика и инвентарь)

| Источник | Зачем |
| --- | --- |
| Component Gallery (`component.gallery`) | Сравнить, как разные системы решают один компонент: анатомия, состояния |
| Design Systems Repo (`designsystemsrepo.com`) | Найти системы по типу продукта и посмотреть их документацию |
| Design Systems for Figma (`designsystemsforfigma.com`) | Если друг-дизайнер работает в Figma — библиотеки, повторяющие код |
| Официальные сайты: Radix (`radix-ui.com`), shadcn (`ui.shadcn.com`), Base UI (`base-ui.com`), React Aria (`react-spectrum.adobe.com`), Carbon (`carbondesignsystem.com`), Primer (`primer.style`), Paste (`paste.twilio.design`), Ant Design (`ant.design`), Polaris (`polaris.shopify.com`), Gestalt (`gestalt.pinterest.systems`), Atlassian (`atlassian.design`), Fluent 2 (`fluent2.microsoft.design`), Mantine (`mantine.dev`) | Читать **документацию компонента**: анатомия, состояния, доступность, «do / don't» |

Правило чтения: смотреть не галерею картинок, а страницу компонента. Ценность систем — в разделах
«когда использовать», «состояния», «доступность», а не в превью.

### 2.3. Реальные интерфейсы (характер и паттерны)

| Источник | Что берём | Чего не берём |
| --- | --- | --- |
| Mobbin (`mobbin.com`), Refero (`refero.design`) | Экраны рабочих приложений: плотность, иерархия, пустые состояния | Пиксели и бренд-приёмы |
| Скриншоты в документации систем | Как выглядит плотный список, таблица, форма | Готовые ассеты |
| Лендинг-галереи (Land-book, Awwwards, SiteInspire, Godly) | Только для входной страницы `/welcome` | Для рабочих экранов — шумно |

Для Solo полезны не «красивые», а **плотные**: Linear, Raycast, Things, Height, Notion, банковские
приложения (для «Финансов»). Ищите не форму кнопок, а как решены: длинный список с ежедневными
отметками, календарь платежей, таблица операций, пустой месяц, ошибка ввода суммы.

### 2.4. Предметные источники (то, чего нет в UI-китах)

| Источник | Зачем |
| --- | --- |
| Financial Times Visual Vocabulary (`github.com/Financial-Times/chart-doctor`) | Какой график под какую задачу: отклонение, динамика, сравнение |
| Документация Recharts и data-viz разделы Carbon / Material | Поведение графиков: оси, легенды, подсказки, пустые данные |
| `refactoringui.com` (книга), `lawsofux.com` | Практика визуальной иерархии и восприятия |
| «Atomic Design» Брэда Фроста (`atomicdesign.bradfrost.com`) | Слои: атом → молекула → организм |
| «Design Systems» Аллы Холматовой, «Building Design Systems» | Процесс и управление системой |
| `inclusive-components.design` | Доступные компоненты на реальных примерах |
| `fontsource.org`, `fonts.google.com` | Шрифты с лицензией OFL, self-hosted |

## 3. Метод: три референса, а не тридцать

Перед работой выбираются **ровно три** источника, каждый со своей ролью:

1. **Механика** — система, устройство которой нравится (например, shadcn + Radix).
   Берём: структуру токенов, состав компонентов, подход к состояниям.
2. **Характер** — продукт, чей интерфейс ощущается «нашим» (например, Linear).
   Берём: плотность, иерархию, тон текста. Не берём: цвета, иконки, композицию один-в-один.
3. **Предмет** — как решается конкретная задача домена (например, банковское приложение для
   «Факт / план / отклонение»). Берём: сценарий и способ подачи чисел.

Каждый разбор оформляется файлом в `design/references/` по образцу `reflect.md`:

```text
Откуда            продукт, экран, дата, чем ограничен разбор (честно)
Что найдено       факты: значения, приёмы, размеры (без оценок)
Что берём         список с причиной «зачем нам»
Что НЕ берём      список с причиной «почему нет»
```

Почему три, а не десять: больше трёх источников не складываются в характер — получается лоскутное
одеяло. Почему письменно: через месяц никто не помнит, почему фон именно такой; документ — это
память проекта, а не отчёт.

## 4. Процесс: восемь шагов

Каждый шаг заканчивается артефактом и критерием «готово». Шаг не начинается, пока не закрыт
предыдущий: система строится снизу вверх, иначе компоненты придётся переделывать.

### Шаг 0. Инвентаризация экранов и состояний

Что делаем: выписываем все экраны и для каждого — состояния (пусто, загрузка, ошибка, успех,
нет прав, офлайн, длинный список). Не «Сегодня», а «Сегодня: 0 привычек / 5 привычек / все
отмечены / отмена отметки / первый запуск».

Артефакт: таблица «экран × состояние» в `docs/…/user-flows.md` или отдельный раздел здесь.
Готово, когда: ни один экран не описан только в состоянии «всё хорошо».

Почему первым: компоненты выбираются по состояниям, а не по макету главного экрана. Пустое
состояние и отмена действия — это и есть продуктовая уникальность, их нет в UI-китах.

### Шаг 1. Три референса

Что делаем: выбираем три источника (§3), снимаем факты, пишем три файла `design/references/*.md`.
Готово, когда: у каждого пункта «берём» есть причина, а у каждого «не берём» — причина отказа.

### Шаг 2. Принципы

Что делаем: формулируем 5–7 принципов, по которым разрешаются конфликты. Принцип проверяемый, а не
лозунг.

| Плохо | Хорошо |
| --- | --- |
| «Интерфейс должен быть красивым» | «Число первично: XP и суммы читаются раньше подписей и декора» |
| «Минимализм и воздух» | «Один экран — одна задача; второстепенное уходит в подпись 13px» |
| «Дружелюбный тон» | «Никаких упрёков за пропуск: текст описывает факт, а не оценку» |

Артефакт: раздел «Принципы» в `design/direction.md`. Готово, когда: любой спор о вёрстке решается
ссылкой на принцип, а не вкусом.

### Шаг 3. Токены

Что делаем: описываем **все** категории значений, а не только цвет:

| Категория | Пример в Solo |
| --- | --- |
| Цвет | `--color-bg`, `--color-accent`, `--color-progress`, состояния (`hover`, `active`, `selected`) |
| Типографика | Шкала размеров и межстрочных, веса, трекинг, моно-числа |
| Пространство | Шаг 4px, набор отступов, ширина колонки, вертикальный ритм секций |
| Радиусы | 6 / 8 / 12 / pill |
| Границы и тени | `1px` низкоконтрастная граница; тень только для слоёв |
| Движение | Длительности `120/200ms`, кривая, правила циклических анимаций |
| Слои | `z-index` по именам (header, dialog, toast, tour) |
| Точки перелома | 390 / 768 / 1024 / 1440 |
| Состояния | `:focus-visible`, `disabled`, `loading`, `error`, `selected` — как отдельные токены, если различаются |

Механика: **два уровня токенов**. Примитивные (`--lavender-500`) и семантические
(`--color-accent`). Компоненты используют только семантические — тогда смена темы не трогает код.

Готово, когда: в компонентах нет ни одного литерала (`#ba9cff`, `13px`, `8px`) — только токены.

### Шаг 4. Примитивы поведения

Что делаем: ставим Radix (или Base UI / React Aria) и фиксируем, **что берём у них, а что пишем
сами**. Как правило: берём фокус-ловушку, клавиатуру, `aria-*`, позиционирование; пишем — вид,
тексты, анимации, состав.

Готово, когда: любой компонент с поведением проверен с клавиатуры и скринридером по APG.

### Шаг 5. Компоненты

Что делаем: собираем минимальный инвентарь под реальные экраны. Для Solo он выглядит так:

| Компонент | Сегодня | Прогресс | Сферы | Финансы |
| --- | --- | --- | --- | --- |
| Button / IconButton | ✓ | ✓ | ✓ | ✓ |
| Checkbox / отметка | ✓ | | | |
| Input / NumberField | | | | ✓ |
| Progress (полоса, кольцо) | ✓ | ✓ | ✓ | |
| Card / Panel | ✓ | ✓ | ✓ | ✓ |
| List row (строка данных) | ✓ | ✓ | | ✓ |
| Tabs / Segmented | | ✓ | ✓ | ✓ |
| Dialog / Sheet | ✓ | | | ✓ |
| Popover / Menu | ✓ | ✓ | | ✓ |
| Tooltip | | ✓ | ✓ | ✓ |
| Toast | ✓ | | | ✓ |
| Table | | ✓ | | ✓ |
| Chart wrapper | | ✓ | ✓ | ✓ |
| Calendar / DatePicker | | | | ✓ |
| Empty state / Skeleton | ✓ | ✓ | ✓ | ✓ |
| Slider | | | ✓ | |

У каждого компонента — паспорт: назначение, анатомия, все состояния, клавиатура, `aria`, «do / don't»,
пример кода. Готово, когда: компонент используется минимум в одном экране и описан.

### Шаг 6. Паттерны экранов

Что делаем: собираем компоненты в сценарии и фиксируем раскладку: где заголовок, где число, где
действие, как ведёт себя длинный список, что происходит при нуле и при ошибке.

Для Solo: «Сегодня» — список и одна кнопка отметки; «Прогресс» — число и динамика; «Сферы» —
радар и список; «Финансы» — два числа и график, монохромно.

Готово, когда: новый экран собирается из существующих паттернов без новых компонентов. Если нужен
новый — это осознанное расширение системы, а не импровизация.

### Шаг 7. Каталог и проверки

Что делаем: делаем компоненты видимыми и проверяемыми. Минимальный вариант без новых зависимостей —
dev-маршрут `/ui` внутри приложения: все компоненты во всех состояниях, рядом — токены. Вариант
потяжелее — Storybook.

Проверки, которые входят в шаг:

- `npm run typecheck`, доменные тесты, Playwright-скриншоты;
- визуальная регрессия: скриншот каталога до и после изменения;
- контраст и видимый фокус;
- `prefers-reduced-motion`;
- инспектор на «AI-slop» (градиенты, стекло, одинаковые скругления).

Готово, когда: изменения в токенах видны на одном экране, а не ищутся по приложению.

### Шаг 8. Управление

Что делаем: договариваемся, как система меняется:

- **Версия**: `0.x` пока система не покрыла все четыре раздела; правило «ломающее изменение —
  мажор».
- **Changelog**: что добавлено, изменено, удалено, и почему.
- **Депрекейт**: старый компонент помечается и живёт один цикл, потом удаляется.
- **Ворота**: новый цвет или размер сначала попадает в `tokens.md`, потом в код. Обратный порядок
  запрещён.
- **Ревью**: изменение системы — отдельный шаг, а не побочный эффект фичи.

Готово, когда: система меняется предсказуемо и никто не «дорисовывает» цвет по месту.

## 5. Как работать с агентом

Работа идёт итерациями, и каждая итерация — один шаг из §4, а не «сделай красиво».

### 5.1. Формат запроса

```text
Шаг: <номер и название>
Цель: <что должно появиться>
Экран/компонент: <где применяется>
Ограничения: <что нельзя — из direction.md и tokens.md>
Готово, когда: <проверяемый критерий>
```

Примеры, которые работают:

- «Шаг 0: собери инвентаризацию состояний для „Финансов“ по `docs/finance/requirements.md`.
  Не меняй код. На выходе — таблица экран × состояние и список пробелов».
- «Шаг 3: разбери `tokens.md` и найди все значения в компонентах, которые не являются токенами.
  Покажи список файлов и строк, ничего не правь».
- «Шаг 5: собери `AmountField` на React Aria NumberField с нашими токенами, состояния
  default/focus/error/disabled, тест на ввод запятой и клавиатуру. Обнови паспорт компонента».
- «Шаг 7: добавь dev-маршрут `/ui` со всеми компонентами и их состояниями. Только dev-сборка».

Что делает агент в каждой итерации: читает документы и код, предлагает решение с причиной,
реализует, проверяет (типы, тесты, скриншоты), обновляет документацию. Что агент не делает без
просьбы: не меняет палитру, не добавляет зависимости, не коммитит.

### 5.2. Чего в запросе быть не должно

- «Сделай красиво» — нет критерия, результат нельзя принять.
- «Поставь библиотеку и перекрась» — это смена темы, а не система.
- «Сделай редизайн» — без инвентаризации состояний превращается в перестановку блоков.

### 5.3. Разделение с другом-дизайнером

- **Дизайнер** ведёт характер: принципы, композицию, иерархию, иллюстрации, разбор референсов.
- **Код и токены** — источник истины о значениях; Figma, если появится, повторяет токены, а не
  наоборот.
- **Спорные случаи** решает принцип из §4 шага 2, а не вкус. Если принципа нет — сначала принцип.

## 6. Как измерять, что система полезна и уникальна

«Уникально» — не «непохоже», а «решает задачу продукта так, как это следует из его модели».
Проверки:

| Критерий | Как проверить |
| --- | --- |
| Скорость до действия | Сколько шагов от открытия до отметки привычки/операции |
| Консистентность | Новая фича собирается из существующих компонентов без новых токенов |
| Доступность | Клавиатура, фокус, контраст, скринридер — на каждом компоненте |
| Понятность без объяснений | 5 человек, 3 задачи: «отметь дело», «найди отклонение», «пойми, сколько до уровня» |
| Стоимость изменения | Правка токена меняет вид во всех разделах, а не в одном |
| Отсутствие «AI-slop» | Скриншоты и инспектор: нет дефолтных градиентов, стекла, одинаковых скруглений |

## 7. План для Solo

| Итерация | Результат |
| --- | --- |
| 1 | Инвентаризация экранов и состояний + три референса с разборами |
| 2 | Принципы в `direction.md` + ревизия `tokens.md` (состояния, слои, движение) |
| 3 | База компонентов: shadcn + Radix, тема на наших токенах, dev-маршрут `/ui` |
| 4 | Первые шесть компонентов: Button, Input/NumberField, Checkbox, Progress, Card, Toast |
| 5 | «Сегодня» на компонентах системы, со всеми состояниями |
| 6 | «Финансы»: AmountField, Table, Chart wrapper, монохромная тема |

Критерий завершения: экран собирается из системы без «одноразовых» стилей, а изменение токена
видно во всех разделах.

## 8. Чек-лист приёмки компонента

- [ ] Только семантические токены, ни одного литерала цвета/размера.
- [ ] Состояния: default, hover, active, `:focus-visible`, disabled, loading, error.
- [ ] Клавиатура и `aria-*` по APG; проверено скринридером.
- [ ] `prefers-reduced-motion` не ломает содержимое.
- [ ] Тёмная тема; тема ступеней не требует правок компонента.
- [ ] Нет внешних ассетов и чужих логотипов; иконки — из выбранного набора.
- [ ] Пограничные данные: пусто, очень длинный текст, 0, отрицательное число, дробь.
