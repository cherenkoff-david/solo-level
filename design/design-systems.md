# Дизайн-системы: что взять за основу

Исследование и рекомендация, ноябрь 2026. Задача: выбрать готовую дизайн-систему, которую
можно установить в Solo, использовать для разделов «Сегодня», «Прогресс», «Сферы» и «Финансы»,
а затем адаптировать под собственный стиль без юридических рисков.

Документ отвечает на три вопроса: что подходит по стеку и характеру продукта, что ставить,
и что нельзя ставить вообще.

---

## 1. Что уже задано в Solo (ограничения выбора)

Любая система оценивается не «сама по себе», а по совместимости с уже принятыми решениями:

| Ограничение | Следствие для выбора |
| --- | --- |
| React 19 + Vite + TypeScript | Система должна работать в SPA, без Next.js и серверных компонентов |
| Tailwind CSS 4, CSS-first, токены в `@theme` | Система со своим CSS-движком (Emotion, Sass, CSS-модули, Panda) конфликтует с токенами |
| Собственная палитра и шкала размеров (`design/tokens.md`) | Нужны «голые» примитивы или компоненты, которые можно переписать под свои токены |
| Тёмный плотный рабочий интерфейс (Linear / Raycast) | Не подходят системы с выраженным корпоративным или брендовым лицом |
| Один пользователь, приватность, self-hosted шрифты | Не нужны тяжёлые enterprise-обвязки; внешние CDN нежелательны |
| Репозиторий публикуется на GitHub | Платные UI-киты и системы с запретом на раскрытие исходников исключены |
| Компоненты должны быть своими | Предпочтение — copy-in (код переезжает в репозиторий), а не runtime-зависимость |

Из этого следует главный вывод: **одной монолитной системы, которую можно «просто установить»,
для Solo нет**. Любая полная система принесёт свой визуальный язык и свою тему, которые придётся
побеждать. Правильная стратегия — собрать базу по слоям из permissive-лицензий.

---

## 2. Слои дизайн-системы

«Дизайн-система» — это не один пакет, а четыре слоя. Их можно выбирать отдельно:

1. **Токены** — цвет, типографика, отступы, радиусы. В Solo уже есть и являются источником истины.
2. **Примитивы** — поведение и доступность: диалог, меню, слайдер, чекбокс, поповер. Без стиля.
3. **Компоненты** — примитивы, одетые в токены: кнопка, поле, карточка, таблица.
4. **Данные** — графики и таблицы: отдельные библиотеки, а не часть UI-кита.

Именно поэтому в таблице ниже рядом с системами стоят Recharts и TanStack Table: для «Прогресса»
и «Финансов» они важнее, чем ещё один набор кнопок.

## 4. Что рекомендуется установить

### 4.1. Основа: shadcn/ui + Radix (MIT)

Причины:

- **Код становится нашим.** CLI копирует компоненты в репозиторий, а не подключает библиотеку.
  Значит, мы можем менять разметку и стили без форка и без ожидания апстрима.
- **Ровно наш стек.** Официальная инструкция для Vite, Tailwind 4 и React 19; никаких Next.js
  и серверных компонентов.
- **Примитивы отделены от вида.** Radix отвечает за поведение и доступность, вид задаём мы —
  это и есть механизм получения собственного стиля.
- **Покрывает все четыре раздела.** «Сегодня» — checkbox, progress, toast, dialog, tooltip;
  «Прогресс» — tabs, chart, table, badge; «Сферы» — chart (radar) или собственный SVG;
  «Финансы» — data table, calendar, popover, dialog, sheet, chart.
- **Лицензия MIT** без ограничений на характер продукта и без запрета на публикацию.

Важная деталь 2026 года: CLI умеет три базы примитивов — `radix`, `base` (Base UI) и `aria`
(React Aria). Рекомендация — **`radix`**: он самый обкатанный и лучше всего документирован.
Base UI — запасной вариант на будущее; React Aria — только если понадобится максимальная
доступность сложных полей.

### 4.2. Данные: Recharts + TanStack Table (MIT)

- **Recharts** закрывает «Прогресс» и «Финансы» без навязывания вида: SVG, цвета через
  `currentColor`/пропсы, данные — наши. Штатный `Chart` в shadcn построен на нём же, поэтому
  отдельная интеграция не нужна.
- **TanStack Table** — headless: логика сортировки, фильтров и пагинации без чужой вёрстки.
  Для «Операций» и истории это дешевле, чем писать своё, и честнее, чем тащить AG Grid.

### 4.3. Иконки: Lucide (ISC)

Единый набор с `currentColor`, тонкая линия совпадает с характером интерфейса. ISC требует
только сохранить уведомление об авторских правах.

### 4.4. Точечно: React Aria для денежных и датовых полей (Apache-2.0)

`NumberField` и `DatePicker` из React Aria дают корректный ввод чисел с локалью, клавиатурой и
скринридером — это дороже всего писать самому, а в «Финансах» ошибка ввода стоит реальных денег.
Ограничение: не смешивать две системы примитивов в одном дереве без нужды — использовать
React Aria **только для полей**, а не для диалогов и меню (там Radix).

### 4.5. Чего не устанавливать

- **Полные системы** (Mantine, Ant Design, MUI, Chakra, HeroUI, Fluent, Atlaskit, Gestalt,
  Radix Themes): принесут вторую тему и второй визуальный язык. Их ценность для Solo — в идеях,
  а не в коде.
- **Polaris** — лицензия ограничивает использование приложениями, интегрированными с Shopify,
  а для сторонних приложений требует, чтобы они были «dissimilar and visually distinct» от
  продуктов Shopify. Для Solo это прямое юридическое ограничение.
- **Платные киты** (Untitled UI, Tailwind Plus/Catalyst) — запрещают раскрытие исходников и
  распространение; публичный репозиторий делает их неприменимыми.
- **daisyUI, Flowbite, Preline** — готовый «вид из коробки», который придётся полностью
  перекрывать; Preline вдобавок требует атрибуции и запрещает конкурирующие продукты.

## 5. Как установить и не сломать текущие токены

Установка — отдельный шаг; ниже план, а не выполненная работа.

1. **Алиас `@/`.** Добавить `baseUrl` и `paths` в `packages/app/tsconfig.json` и
   `resolve.alias` в `packages/app/vite.config.ts` (иначе CLI не сможет писать импорты).
2. **`components.json`** в `packages/app` с указанием нашего CSS:
   `"tailwind": { "css": "src/styles/index.css", "cssVariables": true }`,
   `"aliases": { "components": "@/ui", "utils": "@/lib/utils", "ui": "@/ui" }`.
3. **Инициализация:** `npx shadcn@latest init -c packages/app --base radix`.
   CLI добавит `@import "shadcn/tailwind.css"` и блок CSS-переменных темы.
4. **Немедленно заменить тему на нашу.** Переменные shadcn (`--background`, `--foreground`,
   `--primary`, `--border`, `--ring`, `--radius`) должны ссылаться на существующие токены,
   а не задавать новые цвета. Иначе появятся две палитры: `@theme` и тема shadcn.
5. **Добавлять только нужные компоненты** (`add checkbox progress toast dialog tabs chart
   table calendar popover sheet input`), а не всё подряд: каждый лишний компонент — это код,
   который мы сопровождаем.
6. **Опционально `npx shadcn@latest eject`** — встраивает `shadcn/tailwind.css` в наш CSS и
   убирает зависимость от пакета `shadcn`. Полезно, когда база зафиксирована.
7. **Проверка после установки:** `npm run typecheck`, `npm test`, Playwright-скриншоты, контраст
   и видимый фокус. Любое расхождение с `design/tokens.md` — ошибка интеграции, а не «стиль
   библиотеки».

Типичные ловушки:

- два набора CSS-переменных с одинаковыми именами (`--color-*` из `@theme` и `--*` из темы) —
  визуально «случайные» цвета;
- радиус по умолчанию `0.5rem`, тени и градиенты shadcn — противоречат `tokens.md` (§3, §5);
- тёмная тема shadcn включается классом `.dark`, а у нас тема задаётся атрибутом на корне —
  нужно привести к одному механизму;
- автоматически добавленные иконки `lucide` в компонентах — это нормально (ISC), но проверять,
  что не появились брендовые иконки.

### 6.1. Что разрешают permissive-лицензии

| Лицензия | Можно | Обязательно |

| MIT (shadcn, Radix, Recharts, TanStack, Mantine, Ant Design, MUI core) | использовать, менять, продавать, включать в закрытый и открытый код | сохранить текст лицензии и уведомление об авторских правах в «копиях или существенных частях» |

| SIL OFL 1.1 (Inter, JetBrains Mono) | встраивать шрифты в продукт | сохранить лицензию; не переименовывать шрифт при модификации, если имя защищено |

На практике для copy-in компонентов уведомление в шапке файла не остаётся, поэтому нужен
отдельный `THIRD-PARTY-NOTICES.md`: имя, версия, лицензия, ссылка на исходник. Это и есть
исполнение требования MIT/Apache.

### 6.3. Товарные знаки и «look and feel»

- **Стиль и идеи не охраняются авторским правом.** Взять композицию, плотность, приём с
  таблицей или графиком — законно. Нельзя копировать конкретные исходники, иллюстрации,
  иконки, шрифтовые файлы и логотипы.
- **Нельзя использовать чужие названия и знаки** в интерфейсе, названии системы или
  документации так, чтобы возникала связь с источником: «Solo Carbon», логотип GitHub,
  «Material» в названии продукта. Внутреннее имя компонента — не проблема, публичное — да.
- **Нельзя выдавать продукт за чужой** и использовать чужие скриншоты как свои.
- **Осторожно с «почти копией».** Даже при MIT-лицензии на код визуальная копия узнаваемого
  продукта (Shopify Admin, GitHub) может дать претензию по недобросовестной конкуренции.
  Polaris именно это и запрещает текстом лицензии.

## 7. Как из базы сделать свою систему

База — это не стиль, а поведение и каркас. Уникальность появляется на уровне токенов и правил:

1. **Токены первыми.** Любой компонент использует только `@theme`-переменные. Если компоненту
   нужен новый цвет — сначала токен в `tokens.md`, потом код.
2. **Свой визуальный язык.** Плоские поверхности, `1px` границы, радиусы 6/8/12, две акцентные
   роли (лаванда — интерфейс, amber — прогресс), монохромные «Финансы». Всё это уже описано в
   `direction.md`; библиотека обязана подчиниться, а не наоборот.
3. **Свои имена.** Компоненты живут в `src/ui/` как наш код; в документации — «компоненты Solo»,
   а не «компоненты shadcn».
4. **Минимальный набор.** Ставим только то, что используется; неиспользуемое удаляем.
5. **Свои состояния.** Пустые состояния, загрузка, ошибки, отмена отметки, «−0 XP» — это
   продуктовые сценарии, которых нет ни в одной библиотеке.
6. **Проверка на «AI-slop».** После интеграции прогнать инспектор и скриншоты: не появились ли
   градиенты, стекло, одинаковые скругления и фиолетово-синие тени из дефолтов.
